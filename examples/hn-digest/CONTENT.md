# Captured-content mode

This is separate from metadata `hn-digest/digest`: enabling content does not enable models for old metadata launches. The explicit reviewed content plugin is created by `createContentExtension` in `content-extension.mts`. Its workflows use the ordinary operator/Discord workflow launch action:

```text
hn-content/content
  └─ story (up to the configured selection limit, maximum three)
       ├─ article container worker ─┐
       └─ capture HN comments ─────┴─ analysis container worker
  └─ deterministic aggregation → one human publish approval → report/outbox/seen
```

Article/comment workers start before either is joined. A parent waits through durable `ops.suspend`, not an in-process polling scheduler. It obtains the complete canonical result with `reap`, validates/persists its receipt, then acknowledges notifications. Grounded analysis starts only after both source branches settle. Stage keys bind logical run, story, stage, attempt and evidence; downstream evidence hashes include upstream worker identity/generation.

## Installation and launch

For this demonstration, the host installs the factory through existing `registerBuiltin` composition, with narrow existing registry/report services and a capture authority. `content-runtime.mts` demonstrates this with the offline SQLite runtime. Reviewed-owner and template admission remain host decisions; input authorization strings are provenance, **not grants**. This is reviewed cooperative code, not process isolation of the plugin itself.

Normal manifest autoload of this service-injected factory is not demonstrated. No HN-specific production bootstrap or daemon-main import is added. A real host must explicitly install the factory and supply its real native-tool authority, immutable reviewed templates, scoped model proxy and audited worker egress policy.

Launch input is explicit (`limit` may be omitted and then defaults to `DEFAULT_CONTENT_LIMIT` in `content-contract.mts`; maximum three):

```json
{
  "instance": "content-example",
  "limit": 2,
  "workers": {
    "articleTemplate": "operator-configured-capture-template",
    "articleMethod": "browser",
    "publicEgressAuthorization": "existing-operator-policy-record",
    "modelTemplate": "operator-configured-analysis-template",
    "modelRoute": "explicit-provider/explicit-model",
    "modelBudgetMicros": 10000,
    "articleBudgetMicros": 1000,
    "modelAuthorization": "existing-model-authorization-record"
  }
}
```

`modelBudgetMicros` is the **whole-run** ceiling for paid article/browser workers **and** synthesis, not a per-stage allowance. Each story gets `floor(whole / selection limit)`; its article ceiling is reserved inside that carve and analysis receives only the remainder. No automatic retries, top-ups or recycled attempt ceilings are introduced. The host checks the explicit provider/model and reviewed template before dispatch; its durable scoped-proxy debit ledger, not plugin counters, is spend authority. A host launch budget smaller than the requested carve cannot fund it.

Use the existing command, with the host-approved input and budget:

```text
pomtree workflow launch hn-content/content --input '<JSON>' --budget <whole-run-micros> --key <operator-key>
```

The tests described here use offline source fixtures and a scripted harness.

## Live composition

`content-live.mts` runs one real end-to-end content flow; it spends money, so run it only with a budget you have chosen. `content-live-runtime.mts` composes the real Docker sandbox with the egress-audit spool, Pi, the budgeted OpenRouter proxy and the reviewed `hn-content` extension; preflight refuses before anything opens when the cap, the Pi catalog price for the route, or the Pi auth key is missing. `content-live-run.mts` launches, decides the single publish gate by flag, enforces a wall-clock deadline and writes the digest, per-story results, cost ledger, egress audit and `assertions.json` (checked by the pure `content-assertions.mts`) to the output directory. Static article capture (`--article-method static-http`, the default) runs host-side through an audited, DNS-pinned transport (the image has no static-capture tool). `--article-method browser` runs a real model-driven browsing worker instead (next section); real-model runs of it are not part of the offline tests.

Bounds: every byte and deadline bound of the content chain is a registry key, never a digest constant. The core keys are tabled in `packages/core/src/config/params-daemon.ts` (`params.ts` holds the composed type); the digest's own keys are declared in `params.mts` (the same `params` array as `manifest.json`, kept equal by a test), and compose as `ext.hnDigest.<key>` with env `POMTREED_EXT_HN_DIGEST_<KEY>`: `ext.hnDigest.articleCaptureBytes` (each article input's `maxBytes`), `ext.hnDigest.articleTextMaxBytes` (article text stored per story, whole, as one retained report), `ext.hnDigest.articlePageMaxBytes` and `ext.hnDigest.articleAnalystReadMaxBytes` (the pages and the read budget of the analyst's article access, see Paged article reading), `ext.hnDigest.articleBrowserCaptureDeadlineMs` (each `browser_capture` call), `ext.hnDigest.articleAuditBodyMaxBytes` (the host's audited fetch), `ext.hnDigest.reportMaxBytes` (the digest workflows' report bound), `report.maxBytes` / `report.workflowMaxBytes` (the daemon's report limits) and the `browser.capture.*` keys the browser worker is given (`maxBytesCeiling`, `rawAllocationMaxBytes`, `textMaxBytes`, `screenshotMaxBytes`, `deadlineMinMs`, `deadlineMaxMs`). The live entry resolves them exactly as pomtreed does (default < the JSON file from `--config <file>`, else `$POMTREED_CONFIG` < env, e.g. `POMTREED_EXT_HN_DIGEST_ARTICLE_CAPTURE_BYTES` < repeatable `--set key=value`), except that `<ENV>_FILE` secret names are recognized but never read; the digest's keys are composed with `extendRegistry` (`LIVE_REGISTRY` in `content-live.mts`), so the retired `POMTREED_ARTICLE_*` and `POMTREED_DIGEST_*` names are refused with a `renamed to` hint and any other `POMTREED_EXT_*` name is refused. Any config error (an unknown key, an out-of-range value, a violated relation such as `ext.hnDigest.reportMaxBytes <= report.workflowMaxBytes`) refuses the run with exit 2 before anything opens or spends, one line per error. `workflow.fetch.userAgent` (env `POMTREED_WORKFLOW_FETCH_USER_AGENT`) is optional: it defaults to the neutral product token `pomtree`, and naming a contact is recommended (e.g. `hn-digest (+https://example.org/contact)`); offline compositions send `TEST_FETCH_USER_AGENT` (`runtime.mts`). The one resolved set builds `ContentBounds` (`content-bounds.mts`), which every check takes by injection (the static worker, the article and story-result checks, the capture argument check, the host verifier, the report renderer); offline compositions use `DEFAULT_CONTENT_BOUNDS`, the registry defaults. The viewport, screenshot fallback heights and settle maxima are the worker's own exports (`packages/agent-image/src/browser-capture.ts`), carried in `ContentBounds`, not copies. The story-result and analysis-shape bounds (`STORY_RESULT_MAX_BYTES`, `ANALYSIS_MAX_BYTES`, `MAX_CLAIMS`, the limitation bounds) stay schema constants: the story result's measured worst case is sized from them. Known gap: until pomtreed's `WorkflowHostOptions.reportCeilingBytes` and `DaemonDeps.containerConfig` are wired (`content-live-runtime.mts`), a non-default `report.*` ceiling is not enforced by the embedded workflow host, and the browser worker runs with the registry defaults, so a non-default `browser.capture.*` value fails closed at the verifier (below).

Choosing the story: `--story-id <HN item id>` (repeatable) processes exactly those items instead of the top stories, so a particular article can be targeted. The ids replace the feed read (no feed request is made); at most 3 and distinct, enforced by `content-live.mts`; `--stories` defaults to their count and must equal it when given (fewer would drop an id silently, more is refused). The same filters apply as for a top story (an id that is unavailable, deleted, dead, or not a story, job or poll fails the run before any child or spend; so does an id whose read threw or was interrupted by a restart, which the summary lists separately as `could not be read (fetch failed or interrupted)` so a transient error is not reported as an unusable story. One bad pick refuses the whole run: valid picks do not run alone, because the operator asked for this set; fix or drop the id and relaunch), and the seen state still applies: a picked story already seen is refused with exit 2 (there is no override; remove the id from the seen state to re-run it). The digest numbers picked stories by their position in the ids given, not by a feed rank (its header reads `Operator-picked stories (order as given)` and the headings `Pick N:`, instead of `Ranked feed position, not velocity`); `run.json` `selection` records `operator-picked` with the ids (otherwise `top-ranked`), and `provenance.json` has no feed entry.

Image: `--image` must name immutable content, a digest pin (`repo@sha256:<64 hex>`) or a local image id (`sha256:<64 hex>`, what `docker build` or `docker inspect --format '{{.Id}}'` prints, so a locally built image can be run). A tag is refused with exit 2: it names whatever the local tag points at when a worker starts, and the browser authority approves workers by this exact string.

Publish gate: `--approval approve|deny` (default `approve`) decides it in-process by flag (approver `operator`, why `live run approve by flag`). `--approval pomtree` is decided automatically too, by the harness, not a human: it leaves the approval pending and runs the real `pomtree` CLI (`node --experimental-strip-types packages/pomtree/src/main.ts decide <approval-id> approve --why "live run approve via pomtree" --key live-pomtree-<approval-id>`) as a child against the entry's own operator socket; `POMTREE_SOCKET` and `POMTREE_TOKEN` are in the child's environment only (never argv, a file or a log; the token is in the redaction list and scrubbed from the child's captured output), and the approver is recorded as `cli:operator`. `approvals.json` carries `decidedVia: "pomtree"` on that approval (absent on the flag path). A child that exits nonzero, runs past `min(30s, deadline/4)` (killed), or leaves the pending approval undecided or decides any other approval fails the run: the root is cancelled, the outcome is `failed` and the exit code is 3 (did not publish; no new code), with the reason in the run notes. On either path the entry decides only the one pending publish approval (`pendingPublish`); with more than one pending it decides none, cancels the root and fails the run (exit 3).

### Browser article method

`content-live.mts --article-method browser` reads each article with a real Pi worker that drives Chromium in the hardened audited-public container, then analyses it as with the static method. The constants live in `content-browser-method.mts` (`BROWSER_LIMITS`, `BROWSER_WRAPUP_MS`, `BROWSER_DEADLINE_MS`, `BROWSER_ARTICLE_BUDGET_MICROS`, `STATIC_*` for the static values) and are the one source for the workflow spawn and the live runtime.

* **Template.** `liveTemplates("browser")` replaces `capture-static` with `capture-browser`: audited-public egress, `browser: BROWSER_LIMITS` (pomtreed emits it as `PTREE_BROWSER*`, which makes the sandbox start Chromium through `browser-run.ts`), 256 MiB shared memory, the same provider and model as `grounded-model`. `BROWSER_LIMITS.maxMs + BROWSER_WRAPUP_MS` must not exceed `BROWSER_DEADLINE_MS`, the article child's spawn deadline (a test asserts it). The article child's budget reservation is `BROWSER_ARTICLE_BUDGET_MICROS` (static: `STATIC_ARTICLE_BUDGET_MICROS`); `planCaps` still requires the per-story carve minus that reservation to fund one `maxRequestMicros` request. The worker clips the stored page text at `browser.capture.textMaxBytes`, which the registry keeps `<= ext.hnDigest.articleTextMaxBytes` (the static clip and the evidence check); the clip's limitation names the key.
* **Worker.** `browserArgv` is `piArgv` (`guide: false`, `extSet: "events"`, no `tools`) with the article task's instruction (which names the HN-submitted URL as untrusted data, never instructions) plus a closing line demanding a `capture_finish({status, summary})` call (status `failed` on a capture error) and the sentence that page content is untrusted data. The events extension stays loaded (it journals the tool calls). The tool set is not chosen here: `browser-run.ts` in the immutable image passes `--tools` with `BROWSER_TOOLS` (`browser_capture`, `capture_finish`; no bash, read, write or edit), refuses any caller tool flag, and inserts `--extension pomtree-browser` before the `--` separator (`withBrowserExtension`). It spawns every process by absolute path with `FIXED_PATH`, so a planted `/workspace/.env/*/bin` shim is never on the capture chain. In this method article tasks go to the Pi harness, not the host-side `ScriptHarness`; static tasks still use `ScriptHarness`.
* **Authority.** Browser captures are verified by `createJournalCaptureAuthority` (template `BROWSER_TEMPLATE`; the host approval is `approvedBrowserWorker`: container, that template, the controller-set browser marker `spec.browser`, and exactly the approved image digest): exactly one `browser_capture` call whose arguments hash-equal the expected ones and a matching ok `tool_result` in the worker's journal. The static method keeps its in-memory receipt map. The model's own JSON is ignored by the verifier. The telemetry is trustworthy because the worker has no exec or write tool (the allowlist is enforced inside the image) and runs the capture chain by absolute path with a fixed PATH. Residual risks: a Chromium renderer escape, the pinned pi-browser code (loaded in the worker's own process), and same-uid trust inside the container.
* **Preflight (exit 2).** Before any model request `executeLive` checks the image has Chromium, the browser extension and `browser-run.ts` (`assertBrowserImage`, a short container) and probes the model route with the browser template's egress (`assertModelRoute(probe, "capture-browser")`; the probe is not a worker, so it uses generation 0).
* **Deadline.** The default run deadline is 10 minutes for static; for browser it adds `BROWSER_DEADLINE_MS` (4 minutes) per story (`liveDefaultDeadlineMs`). `--deadline-ms` overrides it. The daemon's session cap, to which pomtreed clamps every spawn deadline without a note, is the larger of the run deadline and that default (`liveSessionMs`), so no agent is cut off before the run deadline.
* **Evidence.** A browser capture is accepted only when navigation was 2xx, the content type HTML and the extracted text at least `ARTICLE_THIN_TEXT`; otherwise `summarize` records `blocked` (a 403, 429 or 503 whose captured text shows a challenge marker), `fetch_error`, `non_html` or `thin` (`other` only when the receipt or artifacts do not verify). A main response with no content type at all (whatever its status) is not `non_html`: the capture fails as `no_response` and the digest records `other`; `non_html` is only a declared type that is not HTML. Text containing a NUL fails capture verification (as the retained-text read would later). Known gap: boilerplate is not checked for browser captures, so a boilerplate-only browser page is analysed. A usable article keeps the body, text, DOM, screenshot and navigation report ids and hashes in `stories/<id>.json`; a not-analysed one keeps only the capture summary, as for static. The worker-timeout scenario is skipped offline because the real deadline is 4 minutes.
* **Audit.** Container rows for the article host and the relays are expected (the `no-private-ranges` assertion exempts the Docker host alias only on the relay ports the run granted: the agent API and the scoped model proxy, `relayPorts`); Chromium also contacts `android.clients.google.com`, `update.googleapis.com` and `edgedl.me.gvt1.com` in the background, which no switch suppresses.
* **Smoke test.** `content-live-browser-smoke.test.mts` runs the real composition with a stub model (Docker and network gated: `PTREE_DOCKER_TESTS`, `PTREE_NET_TESTS`, `PTREE_E2E_IMAGE`). Its article is a public page because a local fixture cannot pass the audited proxy (it denies private and host addresses) or `checkPublicUrl`. Its egress-audit ingest now uses sandbox-docker's validator, and its retained-report readback reads as the root agent; it has not yet been re-verified by a gated run since that fix.

Output files (`workers/<story id>.json` per article attempt holds the worker's sandbox exit and closed exit cause, its tool errors (the output of a failed result only; a successful result, which may hold page text, contributes its size), harness errors, the operator-only capture diagnostic when it journaled one (`diagnostics`: the browser extension's `browser-capture-failure` entry with its bounded, redacted stderr tail, net error and pomtree failure, which reaches the journal as a harness `error` event carrying the `operator-diagnostic` prefix and is lifted out of `errors` by `content-live-workers.mts`), published report names and hashes and, when it published one, the redacted navigation log, all bounded and path-free (`content-live-workers.mts`); `workers/<story id>.analysis.json` per analysis attempt is the analyst's account from the journal: each tool call (turn, name, page, outcome, duration, `attempts` (an `article_page` read's poll count from the tool result `details`, 1 when the page was published at once, null when absent or malformed), closed failure cause, never tool text), each turn's start and end, the child's wall time and exit, the final stop reason, and the paging facts (pages offered versus read, text bytes offered, total and read, the fraction of the read budget used), all bounded and path-free (`content-live-analyst.mts`); `run.json` lists both files and repeats the paging facts per story, and `provenance.json` repeats the exit, cause and last failed tool error per article, plus the worker's closed capture cause (`captureCause`) and, where the cause hides what happened, a closed `captureReason` (`runtime-error`: cause `other` with a non-empty stderr tail, which stays in `workers/<id>.json`), plus a one-line analyst summary; every article worker that ran is written even when the root ended failed with no result (workers are found by the registry name `article-<id>`), and then `provenance.json` lists the story with its worker summary and no capture account; metadata only: no bodies, URL paths or query strings in audit rows): `digest.md`, `stories/<id>.json`, `stories/<id>.rejected.json` (only for a story whose analysis was rejected: the model's raw analysis JSON as received, cut at `REJECTED_RAW_MAX` characters with a truncation marker, the overall failure string, `claimCount` (number of claims in the model's output when it parsed as a JSON object with a claims array, else null), `outputBytes` (byte size of the model's raw output as JSON, 0 when it was not JSON data) and `limits` (`{maxClaims, maxBytes}`), so a limit violation stays diagnosable though `raw` is cut, and one verdict per citation from `explainRejection` with `section`, `claimIndex`, `citationIndex`, `kind`, `quoteLength`, `normalizedLength`, `found` and `reason` of `ok`, `too_short`, `not_found` or `wrong_source`; the digest line is unchanged), `cost-ledger.json`, `model-calls.json`, `egress-audit.json`, `assertions.json` (the checks plus their `inputs`: seen ids, approvals, retained hashes, expected authorities), `approvals.json` (each approval with its rungs and decision journal), `provenance.json` (feed origin, item ids, per-item sha256 and fetch time, per-story article capture facts), `run.json`, and `host-audit.jsonl`. `host-audit.jsonl` is appended as host fetches happen (an `open` and a `final` row per call), so a crash keeps the rows. In `egress-audit.json` container rows keep `bytesIn`/`bytesOut` separately and pass through `denyReason`, `limitKind`, `errorClass` and `admittedAt` when present; host rows carry a hashed URL, the pinned peer (`peer`/`pinnedPeer`, set only once a response arrived; `dialled` records the address a failed dial targeted and is never proof of a connection) and a closed `errorClass` (`dial`, `reset`, `timeout`, `protocol`, `bound`, `internal`).

An article larger than its byte cap is truncated, not rejected: the evidence carries `truncated` and `bytesRetained`, the receipt lists a limitation, and the analysis covers only the retained prefix. Its host audit row is outcome `complete` with `truncated: true` and `bytes` set to what was read (outcome `error` is kept for real failures), so `fetch-audited` passes it without a warning. The digest repeats that limitation under the story (`Limitation:` line), and `provenance.json` records the flag and retained size. `truncated` covers the raw body only. The text clip (`ext.hnDigest.articleTextMaxBytes` UTF-8 bytes for static, `browser.capture.textMaxBytes` for browser; the `Limitation:` line names the key) is the separate `textTruncated` on a usable article, repeated in `provenance.json` beside `truncated`.

Limitation lists have one bound per layer, all in `limitation-bounds.mts`: the verifier accepts at most `NAVIGATION_LIMITATIONS_MAX` lines from a browser navigation log, a verified article holds the host's `BROWSER_HOST_LIMITATIONS` plus those within `ARTICLE_LIMITATIONS_MAX`, and the story evidence holds at most `STORY_LIMITATIONS_MAX`. `limitation-bounds.test.mts` checks the chain against the real worker's worst-case output.

`model-calls.json` has one row per `ext.pomtreed.model_settlement` journal entry (requestId, agent, story, model, tokensIn, tokensOut, optional `cacheReadTokens`/`cacheWriteTokens` when the settlement carries them, micros, upstreamStatus, latencyMs, route, `errorClass` on failed calls, settlement kind, plus the agent's 0-based `turn` ordinal, `toolCalls` the response produced, and `settledAt`/`startedAt` ISO times); with no such entries it is `{"rows":[],"warning":...}`. The assertion `analyst-tools-only` fails the run when any journaled analyst tool call is not `article_page` or `analysis_result`. The assertion `model-calls-match-ledger` requires, when rows exist, unique requestIds and a micros sum equal to the cost-ledger total. The model-debit table is separate from `model-calls.json` and can also hold a cancelled row whose request id ends in `:probe`, with zero charge. It is a zero-micro reservation the model proxy makes to read an agent's remaining budget when a request's full reservation does not fit (`reserveWithClamp` in `packages/pomtreed/src/model-proxy/service.ts`, which then reserves the smaller amount under the real request id), or to tell an invalid credential from a refused request when the store cannot authorize read-only; it is cancelled immediately and never settles, so it is not a model call and never counts toward spend. It appears once per request that took one of those paths, not for every request. In `egress-audit.json`, host rows made before any story exists (the HN feed and item fetches) carry the closed marker `story: "feed"`; `unattributed` means unresolvable. On model-call host rows `durationMs` is the time to response headers (time to first byte), not total latency (that is `latencyMs` in `model-calls.json`), and model-call `bytesIn` is the response Content-Length (0 when absent): the audited fetch never tees the body.

Model upstream rows (our own configured API only) additionally carry `route` (request path, no query) and `upstreamStatus`; article and HN rows never carry a path. `agent`, `requestId` and `model` pass through to `egress-audit.json` when the record has them. The model fetch takes an optional third `ctx` argument (`{ agent, requestId }`) from the proxy: when present the row carries that `agent` and `requestId` from its `open` row on (ctx wins over the response `x-request-id`) and is passed through to the inner fetch unchanged; when absent nothing is invented. An `open` row has `outcome: "pending"` until the call settles; a `pending` row that never gets a `final` row means the process died mid-call (or the body was never consumed), and `fetch-audited` warns about it. The model upstream base is the `baseUrl` of the Pi catalog entry for the route (`anthropic/claude-haiku-5.5` on `openrouter` is `https://openrouter.ai/api`, so Pi's `/v1/messages` becomes `https://openrouter.ai/api/v1/messages`); the entry refuses with exit 2 when the entry or its `baseUrl` is missing or is not on `openrouter.ai`.

Exit codes: 0 published and every assertion held; 2 refused before any model request (flags including the removed `--seen-file`, caps, price, auth, catalog `baseUrl`, unreachable model route, a missing state dir, an unopenable, too-new or corrupt seen state, a bad `--seen-import` file (validated before the preflights), an unusable `--seen-export` path; the import is merged only after the browser-image and model-route preflights and the picked-story seen check (which counts the import's ids too), so a run refused there leaves the stored seen state untouched); 2 also covers any config error (`--config`, `--set`, env; one line each); 3 the run did not publish, or published without an analysed story (the `analysed-stories` assertion: a requested story count above zero with zero analysed stories is never a success, even after approval and publication; the entry logs `did not produce an analysed story`), or published with no usable article because every URL-bearing story's article was dropped for a worker or verification reason (the `usable-article` assertion; the entry logs `did not produce a usable article`; a drop for a page property such as thin, boilerplate, non-HTML, blocked or an HTTP error does not count), or found more than one pending publish approval; 4 any other assertion failed; 5 the run published and every assertion held, but the seen state or its `--seen-export` file could not be updated (see below; any 3 or 4 keeps its own code). Under zsh the exit status of `node examples/hn-digest/content-live.mts ... 2>&1 | tee log` is `${pipestatus[1]}` (`$?` is tee's); prefer `node ... > log 2>&1; echo $?`.

### Seen state (`--state-dir`, `--seen-import`, `--seen-export`)

Each live run uses a fresh private runtime directory, so without persistence every run would re-select the same top stories. The seen set is therefore persisted by default in the state database `<state dir>/state.sqlite`: owner `hn-digest`, key `seen/hn`, value `{ "ids": [<ascending>], "updatedAt": "<ISO>" }`. The state dir is `--state-dir <dir>`, else `POMTREED_STATE_DIR`, else `~/.pomtreed` (the same resolution as `packages/pomtreed/src/main.ts`). `state.sqlite` is a separate file next to the production `pomtreed.sqlite`; the digest never opens, migrates or creates `pomtreed.sqlite`. A production pomtreed and a digest run may use `state.sqlite` at the same time (WAL and a busy timeout; writes are compare-and-set, see below). The model is in `docs/state.md`. The per-run temporary daemon database of the live runtime is unrelated and unchanged. That per-run directory (`hnl-*` under the OS temp dir: the daemon database, reports with article bodies, sessions, the default base repo) is removed when the run ends, including when the runtime fails to open; pass `--keep-run-dir` to keep it for debugging (its path is then printed).

The ids travel in the launch input as optional `seen` (at most `SEEN_MAX`, 2000, so the root's suspension state keeps room for its other fields; unknown keys are still refused) and seed the root's seen set only when no saved root state exists, so restarting the same instance is unaffected. The stored value obeys the same rules as the interchange file `{ "version": 1, "seen": [<positive integer story ids, strictly ascending>], "updatedAt": "<ISO>" }` (`parseSeenFile` validates both).

- Flags: `--state-dir <dir>`; `--seen-import <file>` unions an interchange file into the stored set after the preflights and before the run; `--seen-export <file>` rewrites the full stored set to a file after a published run that added ids. `--seen-file` no longer exists (unknown option, exit 2).
- Start (exit 2, before any model spend): the state dir is missing or not a directory (it is never created, so a typo cannot start a new empty store); the database is newer than this code or cannot be opened; the stored value is corrupt; the import file is missing, corrupt or of another version (the database is untouched); the export directory is missing or `<file>.lock` is held. A missing document is an empty set and is not created yet.
- End: only a `published` run adds anything, and only the ids in the root result's `entryIds` (stories with validated analysis). A denied approval, cancellation, failure, a run with zero analysed stories, and stories published without validated analysis (retried next time) leave the stored set unchanged.
- Write: a compare-and-set merge (read the document and its `rev`, union, put with `expectRev`, a fresh idempotency key per attempt), up to 5 attempts on conflict; concurrent runs therefore never lose each other's ids. A save that adds nothing is not rewritten, so importing the same file twice is idempotent. If more than 2000 ids accumulate, the highest (newest) are kept.
- Export: written under an exclusive `<file>.lock` (`O_EXCL`), to a temp file in the same directory, fsynced, then renamed. A lock left by a dead run is never stolen: delete it by hand after checking no run is active. Importing a file and exporting it again with the same clock reproduces its bytes.
- Failure: if the store save or the export fails, the published result and output files stand, the entry prints `PUBLISHED, but the seen state was NOT updated: <reason>. Story ids to add by hand: [...]` (an export failure reads `export failed: <reason> (the stored seen state WAS updated)`), and exits 5 (or keeps 3/4). The update is never dropped silently.
- Inspect and reset: `pomtree state show hn-digest seen/hn`, `pomtree state rm hn-digest seen/hn` (the next run starts from an empty set and re-digests the top stories).
- A run whose every candidate is already seen is the existing no-op (no approval, no report, exit 3).

Why a database file under the state dir: it is the operator's visible, erasable state (nothing is hidden in browser or opaque storage), now shared with other extensions through one audited, quota-bounded API instead of one ad hoc file per tool; `--seen-import` and `--seen-export` keep the plain-file form for editing and backup.

Before any launch the entry runs a model-route preflight (`assertModelRoute`): a short container with the grounded-model worker's real egress and network shape makes one unauthenticated request to the scoped model proxy, with no model call and no spend. If the route is unreachable the entry exits 2 with `model proxy unreachable from container via <url>: <reason>`. The `grounded-model` template uses egress kind `registry` with the empty manifest, which grants only the node relay endpoints (the agent API and the model proxy) and no public host; `none` grants no relay and would cut the worker off from the model. Known gap: there is no explicit model-only egress kind, so this relay-only registry grant stands in for it.

`content-live-smoke.test.mts` is the no-spend end-to-end check of this composition: the real Docker sandbox, Pi in the agent image, scoped proxy and audit collector, with a local stub as the model upstream (`content-live-stub.mts`) that serves only the path the catalog-derived base and Pi's request path give (a synthetic anthropic-messages catalog fixture, the production derivation; every other path is a 404), a sentinel upstream key and fixture HN/article sources. A negative variant composes the old doubled `/api/v1/v1/messages` path and asserts the stub 404s, no story is analysed and the run exits 3. It also reintroduces egress `none` and asserts the preflight aborts before the stub is contacted. It skips unless `PTREE_DOCKER_TESTS=1` and `PTREE_E2E_IMAGE` names an agent image built from the checked-out revision.

## Source authority and artifacts

* HN comments use the existing official exact-host API capture and normalization. Only the first two selected depth-1 children are sampled, in ranked display order. Deleted/dead/missing context stays in the receipt. Sample sentiment is never representative HN/community sentiment; one usable comment is forced to `unclear`.
* `article-worker.mts` is a mechanical static-reader adapter requiring an actual worker's injected audited transport, scoped publisher and host record callback. It has no ambient fetch fallback. It follows bounded public redirects, preserves original/final URLs, bounds bytes and extracts static article text without executing JavaScript. It does not pretend HN story text is an article or claim browser proof.
* Browser workers invoke the registered `browser_capture({url,maxBytes,deadlineMs})` native tool, which runs the immutable image helper via argv and cancellation; the worker has no bash. Raw main HTTP response entity bytes, rendered DOM, mechanical DOM innerText, PNG screenshot and navigation JSON are distinct artifacts. Entity bytes may already be content-decoded; they are not wire capture. Mechanical DOM text rests on the tool-allowlist and fixed-PATH boundary above (with its residual risks), not on a reconstruction with a pretend host DOM parser, independently attested by another agent, or cryptographically attested.
* `content-authority.mts` accepts one direct receipt JSON only from matched host-ingested `browser_capture` call/result events, exact expected URL/byte/deadline arguments, worker generation and `approvedBrowserWorker` (template, browser marker, approved image digest). The telemetry is trustworthy only because the worker has no exec or write tool and runs the capture chain by absolute path with a fixed PATH; residual risks are a Chromium renderer escape, the pinned pi-browser code (in-process) and same-uid trust. Bash stdout, model result JSON and plausible report IDs are insufficient. Native invocations are counted even when they fail or return malformed output: a second invocation is rejected. This is not an upstream exactly-once guarantee and cannot roll back source requests already dispatched.
* Captures independently cap the main HTTP entity and rendered DOM at `ext.hnDigest.articleCaptureBytes` each, mechanical normalized text at `browser.capture.textMaxBytes` (UTF-8), the PNG at `browser.capture.screenshotMaxBytes`, and the native invocation at `ext.hnDigest.articleBrowserCaptureDeadlineMs` (all from `ContentBounds`, above). The verifier requires the navigation log's recorded limits (`extraction.maxBytes`, `limits.textBytes`, `limits.screenshotBytes`, `limits.maxBytes`, `limits.deadlineMs`) to equal its own resolved bounds, so a worker that ran with other bounds (an image or daemon skew, or tampering) is refused. A clipped raw body retains exactly the bound (no slack); a clipped DOM retains between the bound minus `CLIP_UTF8_MAX_BACKOFF` and the bound; the settle wait records at most `BROWSER_SETTLE_POLLS_MAX` samples and `BROWSER_SETTLE_WAIT_MAX_MS`. Navigation must bind the actual invocation limits and every artifact reference; text clipping must explicitly declare truncation/limitations and the retained exact clipped bytes. These bounds do not claim to limit all redirected/page-asset downloads. Outer child/workflow deadlines and cancellation remain authoritative.
* `content-evidence.mts` reads only a live caller's direct owned child, verifies generation, custody, hashes, byte bounds and source bindings, and copies the actual artifacts to root-owned retention **before reaping**. A durable verified-evidence marker precedes reap; the canonical full receipt is then persisted before ack/downstream spawn. Tests remove child artifacts and reopen SQLite to verify root bytes, hashes and MIME metadata. PNG remains `image/png` and navigation remains `application/json`; raw/DOM HTML intentionally remain inert `text/plain`.
* The audited-public worker transport uses networking disabled (`--network none`), loopback TCP bridging through a read-only shared UDS to the audited proxy sidecar. No direct host article fetch is used. Public redirect/assets policy belongs to that actual worker and its proxy; HTTPS CONNECT audit alone is destination audit, not evidence of page intent.

Static article text is extracted without scripts, styles or tags; a trailing unterminated tag left by the byte cap is dropped and NBSP/Unicode spaces become ordinary spaces. Text shorter than `ARTICLE_THIN_TEXT` characters is `unsupported` with limitation `too thin to ground`: no article claims are permitted, the comments-only analysis proceeds, and the digest shows the article as unavailable with that limitation. A page whose extracted text is a tiny fraction of its markup is also `unsupported`, with limitation `page is mostly markup/boilerplate (N chars of text in M bytes)`: when the capture was truncated at the byte cap, text under `ARTICLE_BOILERPLATE_TRUNCATED_RATIO` of the retained bytes and under `ARTICLE_BOILERPLATE_TRUNCATED_TEXT` characters; when not truncated, under `ARTICLE_BOILERPLATE_RATIO` and `ARTICLE_BOILERPLATE_TEXT`. A repository page captured at the byte cap showed why: about 700 characters of page chrome and file listing passed the thin check, and the model cited the file listing as an article claim. As with thin articles, no article claims are permitted and the comments-only analysis proceeds.

When an article is not analysed, the reason is kept rather than replaced by a generic line. The host re-derives it from the retained body bytes (`summarize` in `content-evidence.mts`; a worker cannot assert it, and the capture receipt's exact key set is unchanged) and stores a small `evidence.capture` beside the null `evidence.article`: `status` (`unsupported` for thin, boilerplate and non-HTML pages; `unusable` for a body over `maxBytes`, an HTTP/fetch failure or a capture that did not verify), `reason` (`thin`, `boilerplate`, `non_html`, `bound`, `fetch_error`, `blocked` or `other`; `CAPTURE_REASONS` in `article.mts` is the single definition), `httpStatus` (the verified response status, 100 to 599, null when there was no response), `textChars` and `bodyBytes` (null when not known), `truncated` (the raw body only), `rawHash` and `textHash` (null when absent), and `finalOrigin` (scheme and host only); a verified browser capture adds `bodyBytesSeen`, `domBytesSeen`, `domTruncated`, `settle` and `screenshot` (null otherwise). `screenshot` is `{bytes, viewportBytes, clip}`: `bytes` is the retained PNG's own length; when the viewport PNG exceeded `browser.capture.screenshotMaxBytes` and the worker retook the top band of the viewport, `clip` is that rectangle (`{x: 0, y: 0, width: 1280, height: 360 or 180}`) and `viewportBytes` the original PNG size, otherwise both are null. The verifier copies them only when the navigation log's `limits.screenshotClip` and `limits.viewportScreenshotBytes` are both present, form a clip the worker can take of a PNG over the bound, and match the log's own `screenshot reduced` limitation. A dropped article then also gets a `Screenshot reduced ...` limitation (a usable one already carries the worker's line). `validateStoryResult` checks the summary against its own bound (`CAPTURE_BYTES_MAX`). It is kept when the article is null, and beside a usable browser article (whose settle and screenshot facts are in no article field); a usable static article already carries the same facts. The story limitation, and so the digest `Limitation:` line, is specific, for example `Article not analysed: page is mostly markup/boilerplate (700 chars of text in 262361 bytes)`; a worker that failed without a receipt gives `fetch_error` with `article worker failed; no capture receipt`, and a receipt that did not verify gives `other`. A summary that says `usable` while the article evidence did not verify is downgraded to `unusable`/`other` with `Article not analysed: verification failed: ...` (`articleOutcome`), so the summary never claims usable what verify refused. `provenance.json` takes each article's `status` and `rawHash` from the retained article, else from this summary (null only when truly unknown), and repeats the summary as `capture`. `blocked` is a 403, 429 or 503 whose retained text (static: the `<title>` and the extracted text; browser: the captured innerText) contains one of `CHALLENGE_MARKERS` in `article.mts` (case-insensitive substring match, nothing executed); any other non-2xx status, or a 2xx page with a marker, is not `blocked`, and any other non-2xx stays `fetch_error`. A `bound` reason is reachable only from the pure `captureStaticArticle` because the static worker truncates at the cap instead; browser captures are summarized the same way (see Browser article method), with `other` only when the receipt or artifacts do not verify. A `bound` summary also carries `bound: {limits, observedBytes}` (present exactly when the reason is `bound`, absent otherwise): `limits` names the configured registry bound(s) by key with their values, one entry when the bound is known (the static reader: `ext.hnDigest.articleCaptureBytes` and the observed body size) and both `browser.capture.rawAllocationMaxBytes` and `browser.capture.screenshotMaxBytes` as candidates when a browser worker reports only the cause `bound` (the worker's closed token does not say which; `observedBytes` is then null, never estimated, so the report cannot yet name one bound). The story limitation quotes the same facts in one sentence (`boundSentence` in `article.mts`), so the agent reading the evidence can document why the page was dropped; classification is unchanged (a page property, not exit 3). A worker that failed also has its closed exit cause in the limitation, for example `article worker failed (signal); no capture receipt`.

A story result is bounded by `STORY_RESULT_MAX_BYTES` (bytes of JSON, enforced by `validateStoryResult`). It was sized from the measured worst case with every bounded field at its limit and escape-heavy filler (asserted in `content-contract.test.mts`) plus margin; real results are far smaller. The bound is larger than the root can hold: its suspension state is capped at `WORKFLOW_STATE_MAX_BYTES` (`packages/core`) and the story ceiling is three, so the root keeps per child only a receipt (child, generation, exit, the `toolFailureCause` the daemon reports when the child's last tool failed, a retained marker in place of the result, and `evidenceHash`), never the body. The join and the post-approval step recover each body from the reaped child row by its owned stable key and compare its hash to `evidenceHash`. The story child's own suspension holds only the evidence (worst case under the cap, asserted). Other limits on the path: `pomtree result` and daemon request bodies and the handoff `summary` have their own caps in `packages/core` and `packages/pomtreed`; the handoff cap applies to the `summary` string only.

Every published model claim carries an exact captured article/comment ID, hash and substring quote. This verifies quotation/hash grounding, not semantic entailment (the digest header says so); quote and captured text (an article's whole stored text, see Paged article reading) are compared after whitespace normalization only (Unicode space separators and tabs/newlines collapse to one space, zero-width characters are removed; no case folding, punctuation stripping or fuzzy matching), the accepted citation records the `normalizedQuote` that matched, and the retained evidence stays the original bytes and hash; a quote must be at least `MIN_QUOTE_CHARS` characters after normalization unless it is the entire, shorter source text. The analysis prompt (`buildAnalysisTask`) states these rules to the model: copy every quote exactly from the provided text (whitespace differences only), at least `MIN_QUOTE_CHARS` characters after normalization unless it is the entire shorter source, prefer a full sentence or clause, and omit a claim rather than cite a short fragment, because one ungrounded citation rejects the WHOLE analysis. The prompt also states the output limits in plain words, interpolated from exported contract constants `MIN_CLAIMS`/`MAX_CLAIMS` (1 to 4 claims), `OBSERVATION_MAX` (observation length) and `ANALYSIS_MAX_BYTES` (whole JSON result size); exceeding any limit rejects the WHOLE analysis, so fewer, stronger claims are preferred. A real run returned 5 and 6 claims and was rejected although every citation was ok. Claims remain tentative. Model/HN-supplied text is newline-collapsed and marker-neutralized (a leading heading, list, quote, rule, table or fence marker is backslash-escaped; other text is unchanged) before entering the draft. This is not a claim that the draft is inert Markdown/HTML, and the analysis prompt fences the evidence between fixed `EVIDENCE_BEGIN`/`EVIDENCE_END` delimiters (any `<<<` inside the evidence is JSON-escaped) with an instruction that it is untrusted data. Article claims without captured article text and fabricated comment citations are rejected. Free model handoff summaries are not published as uncited aggregate claims. Aggregation copies validated claims and explicit limitations; missing branches cannot be silently promoted into evidence.

## Paged article reading

The article text is not in the evidence. A usable article carries `textReport` (the root-retained report holding the whole stored text), `textHash` (its sha256, equal to the report's) and `textBytes`; there is no inline `text` (`ArticleEvidence` in `article.mts`). The stored text is whatever the capture kept up to its bound (`ext.hnDigest.articleTextMaxBytes` for static, `browser.capture.textMaxBytes` for browser); a longer page is clipped and marked `textTruncated` with a limitation naming the key. The browser capture refines the region (`packages/agent-image/src/main-content.ts`, `snapshotInPage`, run inside the page): it takes the largest `<article>`, else `<main>`/`[role=main]`, else `<body>`, hides page chrome inside that root (nav, aside, header, footer, dialogs and the navigation, banner, contentinfo, complementary, search and dialog roles, hidden, script, style, noscript and template elements) while reading its `innerText`, and restores the page. An article or main root counts only with enough text, both absolutely and against the whole body; a root whose stripped text would be empty or a sliver falls through to the next, and when none qualifies the previous region (first `<article>`, else `<main>`, else `<body>`, as is) is read, with the navigation log's generic first limitation replaced by `Unrefined region read; tier_rejected: article=<code> main=<code> body=<code>` (per tier `none`, `small(chars=N)`, `empty(before=N,after=0)` or `sliver(before=N,after=M)`: sizes and closed codes only, so a live fallback says why). `snapshotInPage` is serialized by Playwright and runs in the page, so it takes everything it needs (including the fallback region label) through its `tuning` argument; `main-content.test.ts` runs its `toString()` in a vm context with no module bindings over every path to catch a free variable. The navigation log's `extraction.region` states which path ran, from the closed set `EXTRACTION_REGIONS` (`main-content/article`, `main-content/main`, `main-content/body`, or the fallback `article/main/body`); the verifier accepts exactly that set (imported, not copied), and the hashes cover the retained text only. The static fetch path is unchanged. The analysis child's spawn deadline is a function of the pages offered, `analysisDeadlineMs` in `article-pages.mts` (a base plus a per-page share, so at most the page ceiling's worth; no article text means no pages). `planPages` never exceeds the page ceiling: when the word-boundary heuristic would, it falls back to hard cuts, and past the ceiling the remainder is reported unread. A hard cut inside a word is marked in both page banners (`ends mid-word` / `starts mid-word`) and the prompt tells the analyst to join the parts of that word with no space; any other page boundary is a word boundary, so a joined quote is not falsely rejected at grounding. The pages are recomputed from the stored text and the page bounds on a resume; if `ext.hnDigest.articlePageMaxBytes` or `ext.hnDigest.articleAnalystReadMaxBytes` changed across a restart, publishing the pages fails with `already exists with different content ... changed across a restart` rather than mixing two plans: resume with the first run's bounds. The analysis deadline's base is the old fixed 60 s, so a comments-only analysis is not halved.

The analyst reads the text in pages. After spawning the analysis child the story workflow reads the whole text back from the retained report (`ArticleVerifier.articleText`, which checks the report's hash, size and the byte bound), cuts it with `planPages` (`article-pages.mts`, pure) into pages of at most `ext.hnDigest.articlePageMaxBytes` text bytes (ending at a space when one falls in the last quarter, always on a code point boundary) covering at most the first `ext.hnDigest.articleAnalystReadMaxBytes` bytes, and publishes each page as a report named `article-page-NNN` under the analyst's own agent id (`ArticleVerifier.publishPages`, idempotent by page name, refused for any agent that is not the caller's child). Each page opens with an untrusted-data banner. The analysis task states the page count, the offered bytes, how to read a page (the `article_page` tool) and any unread remainder, and requires the analyst to read every offered page before submitting (calls may run in parallel; the page budget already bounds the cost; claims must cite text read; no summary from page 1 alone). `workers/<id>.analysis.json` records `pagesOffered` and `pagesRead`, so a shallow read is visible. Because pages end at a word boundary they average a little under the page bound: the default read budget of 262144 bytes at 16384 bytes per page offers 17 pages of about 15 KiB, so the count is about 16 or more, not a fixed 16. The text past the read budget has no page, so the budget is structural: the analyst has nothing else to read. A configuration whose page exceeds the read budget is refused at startup by the registry relation, and `planPages` refuses it too.

What the analyst can call. The analysis worker is a Pi container on the relay-only egress template (the agent API and the scoped model proxy, no other host), and it has exactly two tools, `article_page` and `analysis_result`, with no bash, read, write, edit, web or jobs tool (the same shape as the browser worker's `BROWSER_TOOLS`). The allowlist is bound to the template, not the caller: the model template declares `allowlist: "analyst"` (a closed profile list in core, `ALLOWLIST_PROFILES`; its tool names and extension path are the one `ALLOWLIST_PROFILE_TOOLS` table in `packages/agent-image/src/allowlist-profiles.ts`, built from `analyst-contract.ts`), the spawn spec carries it, and pomtreed's `command` resolves it through `harnessArgv` (`piArgv({ allowlist })`); an unknown profile is refused and a spec with the profile can never get the default loadout. The analysis spawn also sets `requireAllowlist: "analyst"`, so the host refuses it (403, before any row or container) when the resolved template lacks the profile. `liveCommand` goes through the same `harnessArgv` and refuses a spec without the profile. The argv is: one `--tools article_page,analysis_result`, the events sink and the analyst extension (`packages/agent-image/ext/pomtree-analyst`) as the only extensions, Pi's MCP, skills, prompt templates, context files and project-local resources off, and no agent guide. The tool names, the page report name, the result key and the result byte bound are one definition (`analyst-contract.ts`) that the host imports. `article_page({page})` takes a whole number 1 to 256, builds the report name `article-page-NNN` from it and the agent's own id from `POMTREE_AGENT_ID`, and runs `pomtree report show` by absolute path with a fixed argv, a fixed PATH and a filtered env, so no model or page text reaches a shell and no other report can be named; it waits for a page that is not published yet and bounds its output. `analysis_result({analysis})` takes the analysis object, requires a summary and the result byte bound, and runs `pomtree result --key hn-content-analysis` the same way, once. A failure reaches the model only as a closed `(cause=...)` token and pomtree's exit code, never pomtree's stderr, so the agent token cannot leak through a tool result. The static-http article method and the browser method both run this analyst. A page is a view, never authority.

Quotes are verified by the host against the whole stored text. `parseAnalysis` and `validateStoryResult` take the resolved text (`ArticleTextResolver`, `ArticleVerifier.articleText`): a quote that is only in a part the analyst was not offered still verifies when it is in the whole text, one that is in no part of it is refused (`not_found`), and a usable article whose retained text does not resolve cannot ground any article quote (the story result is refused). The run assertions re-check every article citation against the whole text the collector read from the retained report (`RunFacts.articleTexts`).

## Publication and recovery

There is one final human-only `publish` approval bound to the exact draft SHA. Denial, timeout, cancellation or all-unusable sources never publish a final report/outbox or mark stories seen. A story whose analysis is unavailable is still shown, but is not marked seen so a later run can retry it. So is a story whose article was dropped for a worker or verification reason (`articleRetryable` in `content-contract.mts`: no capture account, reason `other`, or a `fetch_error` with no HTTP status), even when its comments were analysed; the digest says `Article capture failed for a worker or verification reason; not marked seen.` A drop for a page property (thin, boilerplate, non-HTML, bound, blocked, an HTTP error) is marked seen as before, since a retry would read the same page. A story URL whose path ends in an obviously non-HTML extension (`NON_HTML_URL_EXTENSIONS` in `content-contract.mts`: pdf, txt, json, csv, common image, audio, video and archive types) is refused before any article worker is spawned: the slot gets the same `none` receipt as a story without a URL and the capture account is `unsupported`/`non_html` with cause `non_html` and the limitation `URL path ends in .<ext>, not an HTML page; no article worker was started` (`urlExtensionOutcome`), the classification the live capture would have reached, so it is not retried and is marked seen. Any other non-HTML URL (no extension, `.xml`, a redirect to a file) is still refused by the capture itself as `non_html`. A run that exits 3 marks nothing seen, so the exit code and the seen state agree: when every URL-bearing story's article worker failed (`usable-article`), a URL-less story that was analysed in the same run is published but not marked seen either, and is retried next time; any other published run (exit 0 or 4) marks exactly the stories in the root's `entryIds`. Zero unseen items (every feed id already seen) is a no-op without children/approval/publication; a feed that returns zero ids is a source fault and fails the run (`HN feed returned zero ids`), never a no-op. Root-owned intermediate capture artifacts are retained independently of final publication approval. The approved final Markdown body is retained both as the actual report and in the structured root result; the result includes source provenance and story evidence.

Continuations retain the same task ID and custody. A different task cannot take over an active instance, reset its attempt reservations, or appropriate a prior task's asks. An explicitly new run after terminal failure requires a new instance; cross-task ask transfer is not implemented by this example. Source GET reservations are persisted before dispatch; an interrupted fetch is not automatically repeated.
