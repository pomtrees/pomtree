# Tasks: agents and deterministic code under one contract

Oct 13, 2026 · companion to [`SPEC.md`](../SPEC.md). Target design. Section 9A records the pluggable-workflow design and its first proof.

Evidence labels: `[verified]` means checked against the code or a cited source (`[verified: file/symbol]` names what was checked), `[inferred]` means reasoned from verified facts, and `[knowledge-only]` means drawn from general knowledge without a source checked for this page. The limits of the evidence are recorded at the end. "Current behavior" notes describe the code and never soften the target above them.

## 1. Idea

`pomtreed` tracks the lifecycle of containerized agents. This design names the general thing a **task**: a unit of work with an id, a parent, a budget and a lifecycle, which exchanges messages with its parent and children. An agent (a container running a harness and a model) is one kind of task. A deterministic task (a fetch-and-diff step, an extension's pipeline stage, the body of a cron fire) is another. Both use the same tree, budget, reaping, journal and message path, so code-based work needs no parallel machinery.

## 2. Decisions

1. **Trees, not DAGs.** Parent/child ownership, cancel cascade, budget carve-out and reaping already exist for agents (SPEC "Agent lifecycle and reaping") and carry over. DAG joins (all/any over shared children, partial failure, budget attribution, cancel across shared children) are out. *Reopen when* a real workflow needs one child to feed two parents and a tree-shaped fan-in with a parent-side merge step is shown to be unworkable.
2. **No new queue primitive.** An edge between tasks is "send a signal to a task's inbox": the `Mailbox` port (`packages/core/src/ports.ts`, `Mailbox`: `send(to, signal, idempotencyKey)`, idempotent `receive`, `peek`). *Reopen when* a measured requirement (throughput, ordering across tasks, fan-out delivery) cannot be met by a per-task SQLite inbox.
3. **A task is whatever implements the signal contract** (section 3). The agent adds a container, a harness and a model on top.
4. **`root` is the daemon-internal supervisor at the top of every tree** and the only path from tasks to the user (section 4). *Reopen when* more than one human principal or tenant needs separate roots.
5. **Vocabulary first.** The documentation says "task" for the general concept and "agent" for the container-backed kind. Rule: "task" means only the general contract and the non-container kind; "agent" is used for anything with a sandbox and for every identifier, route, type and lifecycle sentence; "task" is never written for a code symbol. `packages/core` keeps `AgentRecord`, `AgentId`, `Registry` and `/v1/agents/...` unchanged. *Reopen when* a second non-container task kind ships and the dual naming causes concrete confusion in the API or code; then rename in one batched revision of the core contract.

## 3. The task contract

A task is any process, in a container or in the daemon, that does the following.

**The daemon guarantees:**
- A stable id, a generation (fencing token; stale writers rejected), a parent, a state in the registry, a budget carved from the parent, and a journal.
- A durable inbox per task. `send` is idempotent by key and dedupes in the store, before any other check. Delivery is at least once: a signal stays queued until acked.
- `child_exited` goes to the parent when a child ends; cancel and timeout signals arrive in the same inbox. [verified] The signal kinds are in `types.ts` (`Signal`); they include `budget_warning` (produced by the watchdog, section 4) and `escalation` (routed per hop, section 4). Level kinds (`LEVEL_KINDS`: nudge, cancel, timeout, pause, budget_exceeded, budget_warning) coalesce latest-wins, so a pending one is replaced by a newer send; payload kinds queue. Each delivered signal carries an id, the send's idempotency key.
- Reaping, orphan cancellation and budget return, as for agents.

**A task must:**
1. Read its inbox without consuming (`peek`), handle each signal, then ack it by id (`POST /v1/agents/self/inbox/ack {ids, idempotencyKey}`; `GET /inbox` always peeks, section 6). Handling must be idempotent, since redelivery is possible.
2. Treat `cancel` as terminal: stop within `graceMs`.
3. Report a typed result and exit status to its parent (`pomtree result` for agents; the same API call for others), with a handoff summary. It may not finish while it holds unreaped children.
4. Send only to addressable tasks (self, parent, children) and know that agent-originated `message` signals carry the sender's generation and are fenced, while daemon-originated signals are issued by the daemon and are unfenced (`Mailbox` comment, `ports.ts`).

**What an agent adds:** a sandbox (template, image, egress), a harness (Pi) that turns signals into steering text, a model gateway key, and yield/resume checkpoints. Container `SpawnSpec` retains its mandatory image; a deterministic task uses a distinct driver-and-input spec selected by the persisted executor discriminator (`types.ts`, `executor.ts`). Its fenced host operations reuse the tree, inbox, budget, result, cancellation and deadline lifecycle without container resources. Interrupted deterministic drivers fail explicitly rather than replaying arbitrary code; workflow-phase repair is a separate host responsibility (section 9A). Reviewed workflows may opt into durable continuation under the same task id (section 9A.6). Named registration and public launch are distinct from this execution primitive.

| | Agent | Deterministic task |
| --- | --- | --- |
| Runs in | container (template) | daemon process or extension process |
| Inbox consumer | `pomtree-mailbox` Pi extension, polling | its own code, via the daemon API |
| Budget | model spend, enforced by the proxy | wall time and any agent children it spawns; no model spend of its own |
| Yield/resume | checkpoint of session and workspace | none by default; opt-in durable continuation for reviewed workflows (section 9A.6) |
| Failure modes | model, sandbox, stall | code error, timeout |

## 4. Root and the message path

Every task sends to its parent. A task whose parent is root sends to root. Root processes what it receives, in order, and acts as the one boundary between tasks and the user. [verified] Built (`daemon.ts` `toMailbox`, `sendToUser`; `to-user.ts` `relayOf`; tests `daemon.rootrelay.test.ts`, `daemon.touser.test.ts`):

- an **escalation** (a task's ask, an approval, a watchdog trip) becomes a `message_sent` journal entry with purpose `ask` or `alert`;
- **root's inbox is a passthrough to the user's output** (both are forwarded, with attribution, with no special case). `toMailbox` relays any signal addressed to root through `sendToUser` instead of enqueuing it; the relay is journaled on the sender's record, keyed by the signal's key, so a replay yields one outbox entry. The pure `relayOf` maps `child_exited` to purpose `status` and a child's `message` to purpose `report` with subject `[from <senderId>] <body>`. The attribution keeps a relayed line from mimicking an escalation prompt, and a plain message never resolves an approval. The status for a root child's exit is therefore the relayed `child_exited`, written before the immediate reap, for every root-child exit including success. With no channel configured the relay is a silent drop. Operator and inbound human messages are not routed through the relay. There are no detached spawns: a child never outlives its parent.
- adapters (Discord) read only the outbox and deliver; they never read mailboxes.

<a id="user-outbox"></a>**The user outbox** is the set of `message_sent` entries on an agent's journal that are bound for the user. There is one entry per configured escalation channel, and each channel's reader consumes its own entries: the messaging adapter through `Daemon.outbox` (`daemon.ts`; adapter side `packages/messaging-discord/src/outbox.ts`), the in-daemon `ui` channel through the operator SSE stream.

The principle behind this boundary is that an exit nobody accounted for must not be forgotten (SPEC lifecycle rules 1 and 2: a child stays a zombie until its parent reaps it). It holds for every parent, root included.

A message is delivered to the user at most once per source event and channel: the `message_sent` key derives from the source (task id, generation, signal), and `send`'s key dedupes in the store, so a retried send or a replayed exit produces one signal and one outbox entry per channel.

**Multi-channel fan-out and first answer wins.** [verified] Root broadcasts to an ordered list of channels (`escalationChannels`, env `POMTREED_ESCALATION_CHANNELS`; `main.ts`; defaults and overrides in [configuration reference](configuration.md#configuration)). `sendToUser` (`daemon.ts`) writes one sanitized `message_sent` per channel, keyed `${key}:${channel}`, so a replay is idempotent per channel. The in-daemon `ui` channel combines journal messages over SSE (`GET /live/messages`, `builtin/observe.ts`), open escalations over `GET /v1/escalations?state=open` and pending approvals over `GET /v1/approvals?state=pending` in one Inbox. Reloads replay the journal; current escalation and approval records determine actionable cards. Open escalation cards use the operator `POST /v1/escalations/:id/{answer,pass}` routes, including when the `ui` channel is excluded. Approvals and stream-only asks use `POST /v1/ui/reply`, which becomes a synthetic `ui:operator` inbound through `receiveMessage` (`api.ts`; the server requires header `X-Pomtree-UI: 1`, `server.ts`). An answer or a decision from any channel is exactly-once: the store keeps the first, and the loser gets an "already answered" or "already decided" receipt (`receiveMessage`, `daemon.ts`). Not run against a live adapter or in a real browser.

Cron attaches fires to root. [verified] `spawnRootChild` spawns with root as parent (`builtin/cron.ts`, `sweepSchedule`), and the overlap check lists root's children (`cron.ts`, `sweepSchedule`). Below root, `finishTail` reaps a child itself only when its parent is root (or the child declared `reap-on-exit`, after the parent was told); otherwise the child stays `exited` until its parent, or its custodian when the parent is done, calls `reap`, which `requireMergeSettled` further gates. Root children are reaped at once, after their status is written.

**Escalation bubbling (built for asks and approvals; budget raises).** [verified] An escalation climbs the asker's ancestor chain (`daemon.ts` hop routing; `approvals.ts` ladder; `Escalation.holder` and `hopDeadlineAt`, moved by `EscalationStore.advance`):
- Each ancestor agent holds it for its hop window, then it moves up. A hop sends an `escalation` signal to the holder, keyed `<id>:hop:<idx>`, so a replay wakes it once. Agent rungs last `POMTREED_ESCALATION_AGENT_RUNG_MS`; human rungs use `POMTREED_APPROVAL_TIMEOUT_MS`, except a `budget_raise` approval, whose human rungs last `POMTREED_BUDGET_RAISE_MS`. Windows are configuration, not constants; defaults are in the [`escalation`](configuration.md#escalation) and [`budget`](configuration.md#budget) key groups.
- Root's hop is the user: an operator-rung escalation reaches root, which relays it through `relayOf` as purpose `ask` with `replyTo` (the escalation id), so a reply resolves it.
- Every ancestor agent is woken at each hop ("always wake"). Mechanical or hybrid hops, resolved by rule without waking the agent, are a possible future option.
- The answer returns to the asker as `human_answer`, whichever rung gave it.
- Holders act through `POST /v1/approvals/:id/decide {decision: approve|deny|pass, grantMicros?, why?}` and `POST /v1/escalations/:id/{answer,pass}` (field `body`), exposed as `pomtree decide`, `answer` and `pass`.
- `budget_warning` is emitted by the watchdog (`warnBudget`, once per generation, advisory and independent of the ladder).
- Budget exhaustion is not terminal. [verified] An agent that exhausts its budget parks (yields with a null wait) behind a `budget_raise` approval that climbs this ladder (`daemon.ts` budget-raise section, `budget-raise.ts`; windows in `main.ts`). The deciding ancestor pays from its own remaining budget, an operator grant draws from root's, and the grant hook resumes the agent at the next generation with a raised budget; denial or timeout ends it `over_budget`. Detail: [economy.md, section 13](economy.md#13-budget-exhaustion-and-escalation).

Known gap: frequent cron fires and relayed progress can push many lines to the user, and no rate limit is applied to them.

## 5. Idempotency end to end

**Target.** Replaying any step of a message's path produces no second effect: no second signal, no second outbox entry, no second Discord post.

**Current behavior.**
- Inbox: [verified] `send` runs under `once("mailbox", key)`, replaying before target and fence checks (`store.ts`, `mailbox.send`); the daemon keys agent messages `${from}:${to}:${key}` (`daemon.ts`, `Daemon.sendMessage`) and child exits `${child}:${generation}:child_exited` (`daemon.ts`, `Daemon.notifyParent`).
- Journal: [verified] `record(..., key)` calls carry deterministic keys for `message_sent` (e.g. `daemon.ts`, `Daemon.ask`).
- Not covered: [inferred] the Discord post itself. The adapter keeps a cursor file and a bounded dead-letter journal (`outbox.ts`, `MAX_DEAD_LETTERS`); a crash between a successful post and the cursor write re-posts. Not traced in `adapter.ts`.
- Daemon-originated `deliver` keys are deterministic (no boot nonce), so a replay after a restart is deduplicated. [verified, `daemon.ts` `Daemon.deliver`: key `${agent}:deliver:${source}`]
- Hop signals are keyed `<id>:hop:<idx>`, so a replayed hop enqueues once. [verified, `daemon.ts` `Daemon.dispatchAskHop`]

## 6. Delivery guarantees at the consumer

**Target.** An unacked signal survives consumer death, container restart, yield and resume, and is delivered to the next consumer. Acks identify signals by id, and an ack is sent only after the consumer has accepted the signal. Reading without consuming is the default.

**Current behavior.**
- Survival: [verified] signals live in the SQLite `mailbox` table until `receive` deletes them (`store.ts`, `mailbox.receive`); the extension polls the inbox, which always peeks, and acks by id only after a successful injection (`mailbox.ts` `pollInbox`, `ackInbox`, the tick). An unacked signal is therefore redelivered after a restart. The extension's `Dedupe` (by id) is in memory only, so a restarted extension may inject a signal twice (at-least-once) [verified, `mailbox.ts` `Dedupe`].
- Failed injection: [verified] a signal whose injection fails is retried each poll; after `MAX_INJECT_ATTEMPTS` (3) the extension logs a note and acks it although it never delivered it, so one bad signal cannot wedge the inbox.
- Consumer dedupe: the usual remedy for at-least-once delivery is to record the processed event id in the same transaction as the consumer's effect (Debezium outbox article, source 21). The extension's in-memory `Dedupe` cannot do that; the daemon could record the handled id durably. [inferred]
- Ids at the port: [verified] the `Mailbox` port has them (`ports.ts`, `types.ts` `Delivered`, store and `testing` fake). The signal id is the send's idempotency key, `peek` and `receive` return `Delivered` signals, and `ack(agent, ids, key)` is keyed-idempotent (repeating a key returns the prior result), order-free, and a no-op for unknown ids.
- Ids end to end: [verified] the daemon API acks by id (`POST /v1/agents/self/inbox/ack {ids, idempotencyKey}`, `api.ts`), `Daemon.inbox` only peeks (`daemon.ts`), the extension dedupes and acks by id, and `pomtree inbox` peeks and then acks exactly the ids it printed (`cli.ts`; a lost ack redelivers). Two identical signals are distinguishable.
- Rejected injection is acked: [verified in comment, `pomtree-mailbox/index.ts` tick] Pi reports a failed `sendUserMessage` through its error channel, not by throwing, so the signal is acked anyway. Known gap: a rejected `sendUserMessage` is not detected.
- Live Pi: delivery is UNVERIFIED against a real Pi. A Pi RPC design over stdin (it needs stdin on `SandboxHandle`) would replace polling and is future work.
- Reading never consumes: [verified] `GET /inbox` always peeks, so a reader that crashes after the response loses nothing. Peek-then-ack by id is the only consume path.

## 7. Bounds and backpressure

**Decision: no inbox bound.** There has been no production blowup and no clear reason for a particular cap. If one is added later, a send past the bound should fail visibly to the sender rather than drop silently. Level-kind coalescing (section 3) already limits repeated level signals to one pending entry.

**Current behavior.** [verified] There is no bound: `send` inserts unconditionally for payload kinds. The only guard is "target not reaped". Message bodies are capped at the API edge only for some fields (see section 8); [inferred] a message body from `pomtree send` is not size-capped here.

Known gap: the inbox is unbounded, and operator and inbound human messages addressed to root are enqueued and never read. Reopen on an actual inbox blowup.

## 8. Sanitization at root

Root is the single point where untrusted text becomes user-facing text. [verified] Built: `toUser` (`to-user.ts`) strips control, bidi and zero-width characters, breaks mentions, and caps length at `USER_TEXT_MAX` with a visible truncation marker, and `sendToUser` (`daemon.ts`) is the one writer of every user-bound `message_sent` (sanitized once, then written once per configured channel), so every ask, alert and status passes it. `USER_TEXT_MAX` is 2000 characters (the ask question cap is unchanged; options stay at 200). `toUser` also defuses escalation ids (`es-<64 hex>`) so a quoted id is not text-parsed as an answer. Ask text is capped at `USER_TEXT_MAX` and persisted as clipped, so the escalation, journal and outbox carry the same text. Tasks and adapters may add their own caps, but correctness does not rely on them; the same clipping applies to deterministic tasks, whose output derives from page text.

Adapter backstop: [verified] Discord rendering truncates to 2000 characters (`render.ts`, `MAX_OUTBOUND_LENGTH`, `renderOutbound`), and `discord.ts` sets `allowed_mentions: {parse: []}`. `toUser` also neutralizes mentions and strips bidi and zero-width characters.

Remaining:
- Agent-bound clips are not user-bound and stay `clipText` (`daemon-util.ts`): `child_exited` handoffs (`SIGNAL_HANDOFF_CHARS`) and dead-letter fields.
- Known gap: the asker is not told that its ask text was truncated.
- `message` signals between agents (`pomtree send`) carry the body unclipped into the recipient's steering text (`mailbox.ts` `formatSignal`). [verified] That is a prompt-injection channel, not a user-facing one; it is out of scope for root but noted.

## 9. Worked example: a cron fire that reads the web

This example uses one deterministic coordinator: fetch, diff and rule matching are internal stages of that task, with optional model-agent children. It does not require a separate tracked node per stage or a launchable flow catalogue. Its single-batch stage shape is a sketch; the per-story stage tree in section 9A.6 supersedes it for stages, and the failure paths below still hold.

1. The schedule `news-watch` fires. Cron calls `spawnRootChild` with the schedule's task and template; the child's task key is `news-watch:<scheduled time>`, so a repeated fire is a recognized duplicate (`builtin/cron.ts`, `sweepSchedule`; SPEC "Cron").
2. The child is a **workflow-plugin task** (section 9A; written `flow` below): a non-container task (target; needs the no-sandbox executor described in section 3) that fetches pages through the extension gateway (`ExtensionGateway`, SSRF-guarded, approval-gated), diffs against stored prior content, and matches items with rules. It runs in the daemon or an extension process and speaks the contract of section 3.
3. For items the rules cannot decide, `flow` spawns **one model agent** per batch with a carved budget and a typed prompt containing clipped page text. The agent returns a result to `flow`, which reaps it.
4. `flow` reports a result (matched items, counts, a short summary) to its parent, root, and exits. Root clips the exit summary (section 8), writes a `message_sent` with purpose `status` (section 4), and the Discord adapter posts it from the outbox.
5. Failure paths: a fetch failure fails the task with a cause; the built cron breaker backs off and pauses a schedule after repeated failed spawns (`builtin/cron.ts`, `sweepSchedule`, `BREAKER_PAUSE_AFTER`); an unexpected agent ask routes through escalation to the user as today.

Steps 1, the agent spawn/reap primitives in step 3, the spawn-failure breaker in step 5, and the escalation path exist [verified]. The internal deterministic executor supplies execution; named workflow registration and canonical launch supply the separate definition and admission boundary (section 9A). Root forwarding in step 4 exists for the exit status and handoff summary (section 4).

**Results.** Arbitrary structured result storage and submission exist: `AgentRecord.result` is `unknown`, and `submitResult` accepts a payload with a required success handoff. Submission durably stores the complete result in the `ext.pomtreed.result` journal event and immediately sends a `child_result` signal with status and clipped handoff. This is not a typed flow-result protocol: neither `child_result` nor `child_exited` carries the complete result. `child_exited` follows container stop, and reaping before then returns "reported but not yet exited". The complete result remains on the registry record and is returned by reap. Root reaps a finished child immediately and relays its summary; a typed flow consumer must use the stored result or journal payload rather than expect the complete output in root's relay or a later root `reap`. Cleanup, selected commits and `pomtree push` to the local daemon are preferred before submission. Uncommitted work blocks reporting until the agent explicitly approves a snapshot commit and local collection with `--save-uncommitted TOKEN`; a save failure blocks result acceptance. The daemon does not run Git in the agent's private clone or publish upstream. The bounded wrap-up window is not a second work phase. See [the process model](../README.md#the-process-model) for the window override.

## 9A. Pluggable workflows and the first proof

Workflows are pluggable, not first-class. The design starts with reviewed in-process code and is always shaped so that it can be extracted. This section is target design. It reuses the task lifecycle of section 3 and adds no parallel lifecycle.

### 9A.1 What is core and what is a plugin

- **Core, first-class:** the generic task lifecycle of section 3 (identity, generation, parent, budget, inbox, journal, cancel, timeout, result, reap, recovery), plus a generic way to launch a task from a registered definition. Core does not know any workflow by name and holds no enumerated list of workflow variants, no per-workflow policy and no workflow-specific branch.
- **Plugin, not core:** a workflow's behavior: its sources, extraction, matching, deduplication, sequencing, report content and what it remembers. A **workflow definition** is data plus a handler: a name, a typed input schema, declared capabilities (network hosts, whether it may spawn model children and with what budget ceiling, report publishing), and a handler that speaks only the task contract. Template selects agent capability; a workflow definition selects reviewed behavior (the handler runs as a non-container task, section 3).
- **Host boundary, portable:** a handler is written to touch the world only through the daemon API a task already has (inbox, spawn/reap of children, result submission, report publish, fetch through the extension gateway, a per-instance durable store scoped to the workflow instance) and receives its input and its fenced identity from the host. It is not to import daemon internals, read other tasks' state or reach stores directly. The same boundary is what an out-of-process host would call, so moving a handler out later changes the host, not the handler contract. The host owns authorization, fencing, deadlines, budget and cleanup; the handler only proposes. The per-instance store is a small host-provided facade for this workflow, not a new generic state port; promote it only on the trigger in 9A.5.
- **Initial hosting is replaceable and is not a sandbox:** the first host runs reviewed code in the daemon process. The capability-limited facade is a contract and a cooperative authority boundary: it defines what correct handlers use and what the host checks and meters. It does not physically prevent in-process code, including the test handler, from using the daemon's ambient privileges, so a buggy or malicious handler could bypass it. Safety rests on review, promotion and trust of the code, not on the declaration. Only reviewed, promoted code is admitted. Generated or unreviewed workflow code receives no privileges and is not loadable until an isolated execution boundary is approved. Out-of-process hosting (the go-plugin/Argo executor shape, section 11.1) is the expected extraction path; process separation alone does not enforce the boundary, so the isolated host must also constrain ambient filesystem, network and credential access. That enforcement design is chosen when a trigger below fires.
- **Registered flow vs template:** launching resolves a definition by name, validates its input, and creates one task through the existing spawn path with a stable key. Unknown, invalid or unavailable definitions are rejected before any task exists. A definition that disappears (unload, reload) must not orphan an admitted run: it finishes or is stopped by the host under the normal lifecycle.

### 9A.2 Launch is one action, behavior stays out of transport

CLI and Discord parse into the same typed launch action and call the same validated command/action implementation that operator commands use. Transports carry arguments and replies only; they hold no workflow logic. Chat launches, reports and replies through this shared implementation, preserving the actor's channel identity, rank, sender allowlist, rate limits and approvals. The adapter keeps its channel-bound host token and is never given an operator token. A chat actor does not gain a template's or workflow's authority merely by naming it: which definitions chat may launch is an explicit authorization decision of the host, defaulting to deny, and any approval already required for chat spawns still applies. Cron resolves the same registered definition. Results and questions return over the existing outbox, `Daemon.ask`/escalation and reply path (sections 4 and 8); no workflow-owned question protocol or reply channel.

### 9A.3 First proof: Hacker News trending digest

The first proof is a read-only digest of new trending Hacker News posts the instance has not reported before, with insights about their content where a model is used. It precedes any browser automation. A keyboard-search style site-specific task is rejected as too narrow to prove the boundary. This metadata-only proof is distinct from the content pipeline of section 9A.6. Its existing plan-confirmation ask is unchanged, and it has no final publication approval. The single final human publication approval bound to the draft hash applies only to section 9A.6, and this proof does not demonstrate it.

**Behavior (all plugin-owned):**
- **Input:** a workflow instance (a named, configured use of the definition) with a feed (default: the ranked front-page list), a bounded item count, and a per-run budget ceiling for any model child. The instance name keys its state.
- **"Trending" is the ranked feed position, explicitly a proxy.** No velocity, score-delta or time-series measure is claimed. Reports say "ranked" and record the rank and fetch time. Measured velocity needs stored history and is a later, separate slice.
- **Source:** the public read-only HN API (default over scraping; reopen if it lacks a needed field), documented in the HackerNews/API README (source 23). `/v0/topstories` is the documented front-page ranking (up to 500 ids, and it can include jobs); items are `/v0/item/<id>.json`. Only `id` is documented as present on an item; `deleted`, `dead`, `type`, `by`, `time`, `title`, `text`, `url`, `score`, `kids` and `descendants` are optional, and `url` may be an empty string. `title` and `text` are documented as HTML, so they are decoded and sanitized as untrusted text before use. Unknown extra fields are ignored. The README says there is currently no rate limit and does not discuss authentication; it does not say what a removed item returns, whether deleted or dead items remain in feeds, or how the ranking is computed, so the handler treats a null or sparse item as skippable and does not depend on any of these. Fetching is bounded: item count, per-request size and time limits, total run deadline, and an allowlisted host through the extension gateway. No HN login, voting, posting, commenting or any write. Item text and linked pages are untrusted input and are clipped before reaching a model or the user.
- **Per-instance seen history:** durable, keyed by the workflow instance and item id, in the instance-scoped store above. It is shared across launch surfaces: a CLI run and a Discord run of the same instance see the same history. Different instances do not share it. Dedupe is by item id set, not a max-id floor, because feeds are not documented as monotonic.
- **Acceptance is an ordered, recoverable sequence, not one transaction.** The report file store, the user outbox (SQLite journal) and the seen record are separate stores and are not committed atomically. Correctness comes from stable keys and phase repair. Each run has a run key derived from the instance and the launch key. Under it: a persisted **run plan** (the selected item ids, ranks and fetch time, written before publishing, with the evidence needed to render the report); a report key (deterministic report id, section 9A.3 provenance); an outbox key (the `sendToUser` key for the user message); and a seen key (an idempotent insert of the plan's reported ids). Phases run in order: plan, publish report, write user outbox entry, mark seen. Each is idempotent by its key, and the run records the last completed phase.
- **Restart repairs; it does not start over.** On restart or retry the host resumes the run from its recorded phase with the same keys and the same plan, so a crash after the report but before the outbox, or after the outbox but before seen, completes the missing phases and yields one stored report and one outbox entry. An item that is not yet marked seen does not mean "new": while a run's plan is incomplete, its items belong to that run, and a later launch first completes it (one active run per instance) rather than building a fresh plan and a second report key. Items enter the seen set only in the final phase, and only those the report actually presented with content. The Discord post itself keeps the existing post/cursor crash window (section 5); this design does not claim exactly-once delivery to Discord.
- **Concurrent overlap:** two runs of one instance must not both report the same unseen items. The accepted default is one active run per instance, enforced at launch with a stable key (a second launch while one is active returns that run or is rejected, as cron overlap does); the idempotent seen insert and plan ownership above are the backstop.
- **Unavailable, failed, malformed, deleted or dead candidates** are bounded and skipped for the current run: each gets at most a small fixed number of fetch attempts within the run deadline, so there is no retry loop, and each is counted by cause in the report. Skipping does not mark an item seen and is not recorded as a processed success. A transient failure (network, timeout, null result) leaves the item eligible in a later run; a deleted or dead item is likewise not marked seen and is re-evaluated cheaply if it still appears in the feed. Only items that were fetched, validated and presented are marked seen. If the feed itself cannot be fetched, the run fails with a cause and marks nothing seen. An empty unseen selection is a successful "no new posts" outcome, not a failure. If candidates were selected but all failed to yield usable content, the run fails with a cause; a run with some skipped items reports partial and says so.
- **Insights:** a model child is optional and bounded by a carved budget. When used, it receives clipped item text and fetched page text and returns a typed result per item; the report distinguishes model-derived insights from extracted facts and links each to its source item. With no model child, or a failed or over-budget one, the report lists ranked titles, links and extracted fields only, labeled as such. Titles alone are never presented as analysis, and nothing unsupported by fetched content is fabricated. The staged form (per-story analysis and sampled sentiment) is in section 9A.6. Model and fetched text is untrusted: it cannot widen the workflow's capabilities or alter what is marked seen.
- **Provenance and report identity:** each report records source URLs, item ids, fetch times, feed rank, instance name, run id, and the model and budget used for insights. Report names and ids derive deterministically from instance and run so a retry yields one stored report (`reportIdFor` in `pomtreed/src/reports.ts`). Text reaches the user through the normal relay; the report carries detail. Links to stored reports follow the existing authenticated report-view access only; access-controlled daemon-reachable artifact links and remote console/report login are separate work and are not part of this proof. No tokens appear in chat.

### 9A.4 Acceptance criteria

Each criterion needs a regression test. Offline fixtures establish the contract; a scripted-source scaffold alone does not prove a useful workflow, and a live run is a separate step that needs explicit authorization for network access, spend and chat.

- **Executor contract.** A non-container execution path with fenced identity, start, completion, cancellation, deadline, child custody and restart handling through the existing lifecycle. It runs offline with no model key or sandbox; a restart loses no child and duplicates no effect. It uses an explicit persisted executor discriminator, not a template flag or a placeholder container spec.
- **Definition registry and host.** Registered definitions with input validation, declared capabilities, an instance-scoped durable store, and reviewed in-process hosting behind the handler boundary of 9A.1. The host rejects undeclared capability use through the facade and meters declared use (a contract check, not isolation: in-process code can still bypass it, so admission remains review-gated). An unavailable or reloaded definition does not orphan a run, and a test handler written only against the boundary runs unchanged under a second, stub host.
- **Launch action.** One typed launch action, forwarded by the CLI and chat; chat authorization is default-deny with explicit allowlisting; launch is keyed and idempotent; cron resolves the same definition. Invalid and unknown input is rejected before creation, a retried launch returns one task, chat and operator authority differ as intended, and no operator token reaches an adapter.
- **HN digest handler.** The definition of 9A.3 against recorded fixtures: ranked-feed ingestion; enforced bounds; deleted, dead and malformed items; seen history shared across launch surfaces and isolated across instances; a crash injected between each phase (plan, report, outbox, seen) resumes with the same keys and leaves one stored report and one outbox entry; transient and permanent skips are counted and not marked seen, with no in-run retry loop; duplicate and overlapping runs; a model child that is absent, failing or over budget; and no reachable write route.
- **Live run.** One real fetch of HN, optionally a small-budget model child, and a chat-launched run that reports and accepts a reply; a second run shows no already-reported items. The reported content is independently inspectable by report id and source links, and seen state is correct after a deliberate restart.
- **Out of scope for the proof:** measured trending velocity, a catalogue or UI, a second host kind, accessible artifact links, parent-driven content stages and durable continuation (9A.6), and browser-based workflows, which keep their own gates.

### 9A.5 Reopen triggers

- Extract the host out of process when a handler needs isolation from the daemon, when generated or third-party workflow code is wanted, or when handler failure threatens the daemon; then choose an isolated host and keep the 9A.1 boundary.
- Promote the per-instance store facade to a shared knowledge or storage port only when a second consumer needs the same history, not before.
- Revisit one-active-run-per-instance if a real workflow needs parallel runs.
- Revisit the ranked-feed proxy when an operator needs actual velocity.
- Add a DAG or a browser core port only on the existing trigger in section 2 or a demonstrated second consumer; neither is planned.

### 9A.6 Parent-driven content workflow and durable continuation

Target design for a multi-stage workflow. It is canonical for stage shape, custody, ordering and recovery rules. API names are breadcrumbs; the source is canonical for signatures and fields. It adds no DAG, no precreated blocked tasks and no new agent state. "Content coordinator" names this workflow task only; the daemon root (section 4) and its policy are unchanged. The single final human publication approval below applies only to this content pipeline and does not change the metadata-only proof in section 9A.3.

**Stage tree.** Each stage is a parent-driven node in the tree of section 2.
- The **content coordinator** is a workflow-plugin task that is a child of root. It selects ranked headlines and persists the selected stories and their provenance as its plan (9A.3). Its name avoids "root", which is the daemon supervisor (section 4).
- Each selected story gets one **story coordinator**, a child of the content coordinator. It starts **article capture** and **official HN comment capture** in parallel. HN comment capture is a deterministic task that calls the official HN API. Article capture is an audited container or browser worker, optionally orchestrated by a deterministic stage. It fetches public pages under the profile in [SPEC.md](../SPEC.md), not through a daemon fetch, and the design does not restate that policy.
- The story coordinator waits for both children to reach a terminal state, then reaps each and validates its complete result. It persists a receipt per child (IDs and hashes), acks the child-result signal, and only then starts **grounded analysis / sampled sentiment**, passing the receipt references as input. Analysis is a bounded model child with a carved budget, coordinated by a deterministic stage. The deterministic driver does not call a provider itself. It reaps analysis and returns a structured story result to the content coordinator.
- The content coordinator joins the story results (terminal children), then starts aggregation. It opens **one human publication approval** bound to the draft's hash through the existing approval mechanism (`openApproval` and `getApproval` breadcrumbs). Approval uses the existing pluggable approval mechanism and does not duplicate it, and agent approvers are excluded. On approval it publishes, writes the user outbox entry and marks the presented stories seen (9A.3 phases). On denial or timeout nothing is published, and the run ends with a cause.
- Custody: a result belongs to the parent that spawned the child. Siblings do not address one another or read each other's custody. Parents message their children, and validated results travel upward.
- Trivial selection and rendering stay as coordinator phases. A child exists only for independently bounded work.

**Wait-then-start.** A dependent stage exists only in the persisted plan until its inputs are durable and it is spawned. No budget is carved and no admission is granted before the evidence it depends on exists, and the evidence is immutable when analysis starts. The cost is that advance tree visibility comes from the plan, not from the registry. Precreated blocked children would need new gating, cancellation and budget semantics, so they are not part of this design.

**Attention.** A child's ask or approval request bubbles through the existing escalation ladder as the same escalation (same id, never a second approval; section 4). A parent in a dependency wait is woken for attention regardless of the wait.

**Durable continuation (opt-in, reviewed workflows only).**
- Scope: a registered, reviewed workflow may opt in. Arbitrary deterministic drivers keep fail-on-interruption (section 3).
- Mechanism: before releasing execution, the workflow persists a continuation snapshot holding its phase and the wait it is in. The task then uses the existing yield, wake and reconcile machinery with generation fencing. On wake, the same task id resumes under a new generation, and the old generation is fenced. Child custody is unchanged: children stay under the same parent.
- Contents: the snapshot holds the workflow phase, the wait condition and plugin state. It has no container checkpoint, workspace or session fields. It is not a new universal key-value store; per-instance state uses the facade in 9A.1.
- Recovery: on restart the host finds existing children by an owner-scoped stable spawn key, including terminal and reaped ones (`findChild` breadcrumb), and does not respawn them. A crash does not spend a second time on a child that already ran.
- Attempts: each stage attempt is reserved in plugin state before dispatch. Budget carve and debit scope are unchanged, and unused carve returns on reap. Attempt counts are a plugin-state guard. They do not claim provider exactly-once execution.
- Operation names: `suspend`, `answerEscalation`, `passEscalation`, `findChild`, `openApproval` and `getApproval`. Field shapes are canonical in source.

**Stage outputs and evidence.** Stages pass IDs and hashes, never paths. Report bodies and evidence are retained in the report store, and a consumer verifies the hash before use.

**Failure and evidence rules.**
- Partial failures are explicit in the story result. Without article evidence the analysis makes no article claims. Sampled HN comments do not represent HN community sentiment broadly.
- If every selected story is unusable, the run fails with a cause. Zero selected stories succeeds as a no-new-items result.
- Cancel, denial and timeout start no further stage and publish nothing. Admitted effects (fetches, spend) are not rolled back. Cancel cascades custody cleanup through the normal reap path.
- Retries are explicit, use new bounded attempt keys and are not automatic loops.

**Not decided here.** Known gap: workflow questions are task-owned. A replacement task may ask again but cannot take over a pending question; whether to ask again or transfer a question durably is undecided, and same-id continuation does not choose it. Provider, model route and live budget are not chosen here. Stub or offline paths do not establish a positive live claim.

## 10. Open questions

Structured-result durability uses the submission contract above.

- Initial hosting is reviewed in-process code behind the task-operation boundary, a cooperative-trust boundary rather than isolation (section 9A). Extraction to an isolated host remains trigger-driven; it must preserve the same authorized task semantics rather than add a privileged execution path.
- No-sandbox execution uses an explicit persisted executor discriminator, not a template kind or placeholder container spec. Named launch resolves a registered definition into this execution choice; it must not expose a caller-controlled bypass around definition authorization. Known gap: cron does not yet resolve a registered definition; it must resolve the same definition rather than create a second launch path.
- Does a deterministic task need yield/resume? No generic suspension. Reviewed workflows may opt into durable continuation under the same task id (section 9A.6). Arbitrary drivers fail explicitly on interruption, and a workflow host repairs persisted phases using stable keys rather than blindly replaying arbitrary code (section 9A).
- Closed the other way: a child-to-root `message` is relayed to the user as purpose `report` with sender attribution (section 4), not rejected. Reopen if relayed free-form progress proves too noisy (rate limiting of relayed pushes).

## 11. Prior art and design comparison

An external survey found no framework that replaces this design; each system below matches one mechanism. What is unusual here is the combination: parenthood as custody, where an exited child is a durable obligation of its parent until the parent accounts for it. Prior art is a source of mechanisms and reopen triggers, not a plan to adopt any of it. Source claims are labeled by whether the primary page was read (access date for all sources: 2026-10-13). This section compares mechanisms; [`docs/prior-art.md`](prior-art.md) compares whole systems.

### 11.1 Prior art by mechanism

- **Wait is not destroy (Nomad task drivers, source 10).** [verified] `StopTask` kills after a timeout but keeps the task's state, so a later `WaitTask` is still valid; `WaitTask` on an exited task returns its exit result at once; `DestroyTask` cleans up a terminated task (`force` also kills a running one) and afterwards `WaitTask` returns `ErrTaskNotFound`; `RecoverTask` re-attaches a task the driver no longer knows, and a failed recovery marks the task `lost`; `SignalTask` is an optional capability. The docs also say `Shutdown` is best effort, since Nomad may not call it before the driver exits. This is the same split as exited versus reaped here, and the same reason cleanup needs a daemon-driven path.
- **Application-defined checkpoints (HTCondor self-checkpointing, source 11).** [verified] The executable decides what a checkpoint contains ("up to you or your software provider"). On exiting with a configured `checkpoint_exit_code`, HTCondor copies the listed checkpoint files to the submit node at once and restarts the executable with unchanged arguments, so the program must look for an existing checkpoint at startup. The exit code is reserved for "checkpoint taken", never completion. Compare the yield handshake (section 11.2, item 4).
- **Progress details and child close policy (Temporal, sources 12-14).** [verified] A heartbeat can carry a payload; after a missed heartbeat the next attempt can read it and continue. A child workflow has a Parent Close Policy: when the parent closes, the service sends each child a cancel request or terminates it, or the child is abandoned; parent and child share no state and talk by asynchronous signals. The nearest analogue here is `orphanChildren` in `daemon.ts`, which has no policy choice: it cancels each open child with a grace period, then kills it [verified]. There is no abandon, reparent or park option. Temporal reconstructs workflows by event-history replay; this design resumes an opaque session from a checkpoint instead. [knowledge-only on the replay contrast]
- **Cancel, kill, purge (Restate, source 15).** [verified] Cancel runs handler compensation and is non-blocking; it needs the deployment to be reachable. Kill stops the whole invocation tree without compensation, "as a last resort". Purge removes a completed invocation; completed ones are otherwise retained "for some time". The two-step stop (cancel with `graceMs`, then kill) and the later reap correspond. Restate's durable futures and suspension were not confirmed from a primary page and are dropped.
- **Suspend and finalizers (Kubernetes, sources 16, 17).** [verified] Suspending a Job deletes its active Pods until resumed. A finalizer is a key in `metadata.finalizers` that blocks removal until the managing controller finishes its cleanup and removes the key; deletion only sets `deletionTimestamp`. Finalizers gate deletion on cleanup, not on a parent consuming a result.
- **Plugin boundary (HashiCorp go-plugin, Argo executor plugins, sources 18, 19).** [verified] go-plugin runs plugins as subprocesses over RPC or gRPC so a plugin panic does not crash the host and any gRPC language works. An Argo executor plugin is a sidecar HTTP server the controller calls with `template.execute`, authenticated by a mounted token; it returns a node phase and may ask to be re-called (`requeue`). Both support out-of-process extensions (section 10) that propose and the daemon commits.
- **Attenuated delegation (Macaroons, source 20).** [verified, abstract only] Bearer credentials carry chained-MAC caveats that narrow when, where, by whom and for what purpose a service authorizes a request, and support decentralized delegation. Prior art for monotonic authority only (section 11.2, item 7).
- **Transactional outbox (Debezium, source 21).** [verified] The state change and an outbox row commit in one local transaction; a relay publishes the row at least once; consumers dedupe by event id recorded in the same transaction as their effect.
- **Wait and orphans (POSIX, source 22).** [verified] `wait`/`waitpid` consume a terminated child's status and return at once if it is already available; children of an exiting parent are re-parented to an implementation-defined system process. The page does not say how long an unwaited status is kept. SPEC's reap and zombie rules follow this model; orphans differ, since they are cancelled rather than re-parented.

### 11.2 Comparison with the code

Each item states the idea, then what the code does. Cites name files and symbols; the code each names was read for this section.

1. **Transactional reap.** The idea: commit the child's reap atomically with the parent's checkpoint advance, so a crash leaves either "old checkpoint, child unreaped" or "new checkpoint, child reaped". **Deliberately different.** [verified] `reapNow` runs the registry transition, then the `reaped` journal record, then `gateway.revoke` as separate calls (`daemon.ts`, `Daemon.reapNow`). Crash safety comes from idempotency keys (`transitionKey`; `Daemon.markOp`, `Daemon.reap`) and from replay of `finishTail` by recovery (`daemon.ts`, `Daemon.replayExitedTails`), not from one transaction. No parent checkpoint is involved: a parent reaps by an explicit call, and an unreaped child stays a zombie that raises an alert (SPEC lifecycle rule 2). *Reopen when* a replay path is found that drops or double-applies an exit.
2. **Wait versus reap.** [verified] Already separate. The parent is told at once (`notifyParent`), and `reap` is a later explicit step that `requireMergeSettled` gates (`daemon.ts`, `Daemon.requireMergeSettled`; SPEC "Agent lifecycle and reaping"). The one violation is root's children (section 4).
3. **Fencing.** The idea: revoke the old generation's credentials before the replacement is authoritative; a lost heartbeat does not prove the old container stopped. **Current behavior.** [verified] Revocation by agent id (`issuedAt <= revoked_at`, `store.ts`, model-debit store `revokedAt`) runs on yield (`daemon.ts`, `Daemon.settleYield`, `Daemon.completePause`), forced resume of a running agent (`Daemon.runResumed`), exit (`Daemon.settleLocked`) and reap (`Daemon.reapNow`); `issueKey` refuses exited and reaped agents (`gateway.ts`, `issueKey`); the daemon API token carries the generation and a stale one is rejected (`api.ts`, the `fence` closure). A forced resume of a running agent (watchdog `kill_resume`, startup recovery; `Daemon.applyWatchdogAction`, `Daemon.reconcile`, `Daemon.resumeAgentNow` with `forced`) revokes the superseded instance's model key before killing it and before `runSegment` issues the new one; `ProxyCredentialGateway.issueKey` stamps the new key strictly later than the last revocation, since `issuedAt <= revoked_at` kills a key (`gateway.ts`). The superseded run's `settle` deliberately skips revocation so it cannot kill the fresh key. A revoke failure fails the resume rather than leaving a live key. Known gap: write-time fencing for storage (a fencing-token check by whoever accepts a write) does not exist; on one host the SQLite checkpoint store rejects stale generations.
4. **Yield handshake.** The idea: a suspend request starts a deadline-bounded protocol that ends in an immutable, versioned checkpoint; a task killed before checkpointing is not reported as suspended. **Current behavior.** [verified] `yield` journals a `pausing` marker, stops the container, reads the session, writes the checkpoint and only then transitions to `yielded` (`daemon.ts`, `Daemon.yield`; SPEC "Yield"); a crash in between is completed by `completePause` (`daemon.ts`, `Daemon.completePause`). Checkpoints are immutable id-and-hash rows; the store stamps a `version` (`CHECKPOINT_FORMAT`, `types.ts`), and rows written before versioning read as version 1. A container that dies without calling `yield` takes the `settle` path to `finish`, so it is classed by exit cause (for example `oom_killed`, `host_stopped`), not `yielded` (`daemon.ts`, `Daemon.settleLocked`) [inferred from the path; not run]. **Gaps.** No yield deadline exists (the only deadlines are session wall-clock, `daemon.ts`, `Daemon.spawnDeadline` and `Daemon.armDeadline`). Known gap: the yield handshake has no deadline of its own. The version field is built.
5. **Sandbox port versus Nomad's driver lifecycle.** [verified] `Sandbox` has `start` (idempotent by key), `attach` (re-adopt after restart; the Recover analogue), `stop`, `kill`, `inspect`, `list` and `reclaimEgressOrphans`; `SandboxHandle.wait()` is the Wait analogue (`ports.ts`, `Sandbox` and `SandboxHandle`). There is no explicit destroy (removal of the terminated container) and no signal call; signals go through the mailbox. `reclaimSandbox` stops the recorded sandbox with the grace period, or kills it only when `force` is true, then clears the registry field for that generation, ignoring errors from either step [verified, `daemon.ts` `Daemon.reclaimSandbox`]. Multi-host executors are future work. Nomad is prior art here, not a decision.
6. **Budget carve atomicity.** [verified] A child's carve counts in full while unreaped; the unused part returns on reap (`lifecycle.ts`, `carve`; `daemon.ts`, `Daemon.spawnNow`, `Daemon.consumed`, `Daemon.reap`; SPEC lifecycle rule 5). Carve and registry insert are not one database transaction, but spawns run one at a time through a promise chain (`daemon.ts`, `Daemon.spawn` and the `spawning` field), so concurrent spawns cannot both read the same remaining budget in one `pomtreed` process. `reap` is outside that chain, but it can only enlarge the remainder, so the race is safe. *Reopen when* more than one controller can accept spawns (high availability, a future multi-host design).
7. **Monotonic authority.** A search of `packages`, `SPEC.md` and `docs` for macaroon, attenuation, caveat, subset and widen terms found no caveat or child-scope-subset mechanism. [verified by search; absence is [inferred]] Authority is monotonic by construction, not by check: every agent token has the single scope `agent`, bound to its id and generation (`daemon.ts`, `Daemon.agentToken`), so there is nothing to widen; peer addressing is limited to self, parent and children (`daemon.ts`, `Daemon.canAddress`); a child's budget cannot exceed the parent's remainder (`lifecycle.ts`, `carve`); agents may use only templates a `mayUseTemplate` predicate grants (`daemon.ts`, `Daemon.spawnNow`), and a spawn is refused when the child's egress or resources exceed the parent's (`egressWithin` and `resourcesExceeded` in `packages/pomtreed/src/daemon/delegation.ts`; SPEC "Spawn and fork"). *Reopen when* agents delegate per-task capabilities (a caveat model becomes worth its cost).
8. **Finalizers.** [verified] Cleanup is daemon-driven and idempotent, not left to the agent: `finishTail` and `reconcile()` replay, `reclaimEgressOrphans` runs at startup (`daemon.ts`, `Daemon.reclaimEgressOrphans`), and the cleanup sweep evicts reaped folders (SPEC "Resume"). Known gaps: cleanup after a reap is incomplete (a child whose commits were only partly cherry-picked keeps a refused workspace prune that is retried on every sweep), and a crash after a merge-conflict resume transition but before the wake leaves the child running, with a retried 409 that reconcile does not pick up.

### 11.3 Build and adopt

Keep as core, own code: the task tree, exited-but-unreaped custody, the checkpoint handshake, the budget carve, escalation ownership, and the transaction boundaries between them. The intended design routes escalations through root to the user outbox (section 4). That is delivered for asks and approvals that reach the operator rung after at least one agent hop (section 4); alerts (zombie, watchdog, quarantine) and top-level asks still go directly through `sendToUser`, and routing those through root is a known gap. Container isolation, placement, blob storage and message delivery stay replaceable behind ports (`Sandbox`, `Placement`, `Mailbox`, adapters). A new dependency such as Nomad or an RPC plugin framework is a decision for the user, with the reopen triggers above.
