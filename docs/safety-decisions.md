# Safety decisions

pomtree is meant to be a small core that handles the hard safety problems out of the box and forces the operator to make the remaining safety decisions explicitly; workflows, agent templates, dashboards and adapters are what users bring. This page is the checkable list of which safety decisions the framework owns, which it forces the operator to make, and which it still decides silently. The third list is the gap list: each entry is a place where the framework picks a behavior for the operator without asking. Configuration keys are named here but their defaults are not restated; the generated key reference is [`docs/configuration.md`](configuration.md). The extension tiers this page instantiates are described in [`docs/extending.md`](extending.md).

Evidence labels: `[verified]` means checked against the code or a cited source (`[verified: file/symbol]` names what was checked), `[inferred]` means reasoned from verified facts, and `[knowledge-only]` means drawn from general knowledge without a source checked for this page. Paths in labels are under `packages/`. Work that is planned is described as planned; anything else is described only as current behavior.

## Supervised use only

The sandbox is for supervised use. Agents run in hardened Docker containers that share the host kernel, which is not a boundary against a hostile agent. Do not run agents you consider hostile, or feed them untrusted input, unattended. The protections meant to lift this limit (the model gateway, egress control and pinned publish) are built but have not been validated for unattended use, so no such use is supported. Nothing in the code enforces the limit; it is documentation only (see the gap list). Other documents link to this section instead of restating it.

**Egress confinement is not complete.** Egress is enforced by a per-agent proxy sidecar, but these paths are not confined: in `audited-public` mode only ports 80 and 443 (plus the proxy's `publicPorts` option) reach public addresses and any other port is refused and audited, so git over SSH is refused and needs an HTTPS remote [verified: sandbox-docker/src/proxy.ts `admit`]; the proxy option is not yet set from a template or configuration key, so no deployment opts in to other ports today; the audit records the requested authority, not content (SPEC.md, "Audited public egress"); and `web_fetch` runs from the host network, not through the sidecar, with its reach set from the template's egress policy and any out-of-scope fetch escalating to an approval [verified: pomtreed/src/ext-gateway.ts `webFetchScope`]. Other documents link here for this limit.

## Class 1: framework-owned invariants

These behaviors are not configurable. No registry key relaxes them, and a template, workflow or adapter cannot weaken them.

**Generation fencing.** An agent's token carries the generation it was issued for, and a resume bumps the registry generation, so a still-running old container's token stops working. The API's `fence` rejects a stale-generation agent token with `StaleGenerationError` on agent-scoped routes [verified: pomtreed/src/api.ts `fence`]. Child creation requested through a host operation is re-fenced inside the requester's serialized chain immediately before the record is created [verified: pomtreed/src/daemon/lifecycle.ts `createFenced`].

**Idempotency keys on every mutating route.** Every mutating agent, operator and extension route requires a non-empty idempotency key (extension routes are checked once at the extension seam, before the handler), in the body (`idempotencyKey`) or, for a bodyless route, as `?key=`; a missing one is a 400 naming the field and the fix (`IDEMPOTENCY_KEY_REQUIRED` and `IDEMPOTENCY_QUERY_KEY_REQUIRED` in `pomtreed/src/error-codes.ts`), consistent with SPEC design rule 4 (the first numbered list in SPEC.md). `pomtree` issues a key per invocation unless `--key` names one. `api.idempotency.test.ts` enumerates the mutating routes from the route sources, so a new route without the check fails it. The one keyless mutating call is internal, not a route: the gateway's `issueKey` issues a fresh model credential per container start on purpose, since replaying a cached credential after a resume could hand back a stale or revoked one [verified: pomtreed/src/api.ts, state-routes.ts, builtin/cron.ts, builtin/reports.ts; SPEC.md].

**A parent cannot succeed with unreaped children.** `assertNoOpenChildren` throws a 409 listing the unreaped child ids, and it runs on both the HTTP result path (when the status is `succeeded`) and the deterministic driver's `submitResult` [verified: pomtreed/src/daemon/lifecycle.ts `assertNoOpenChildren`, `submitResultNow`]. A `failed` result skips the check (`submitResultNow` guards it with `status === "succeeded"`). The failed-result and exit-without-result paths were not traced end to end; the exit tail described next is what handles children there.

**No child outlives its parent.** When a parent exits, `finishTail` calls `cancelChildren`, which calls `orphanChildren`, which calls the orchestrator's `cancel` on every non-done child with the configured grace period [verified: pomtreed/src/daemon/lifecycle.ts `finishTail`, `cancelChildren`, `orphanChildren`; SPEC.md Lifecycle rule 4]. There is no per-spawn or daemon-wide setting that changes this; a per-spawn `onOrphan` policy (`cancel`, `adopt-suspend` or `adopt-continue`, inside the child's existing reservation) is planned but not built. A failed cancel is only journaled (an `error` entry keyed `<child>:orphan-cancel-error`); it is not retried in this path and does not stop the parent's exit [verified: same symbols]. The invariant covers live children only; exited children are a custody question. Children of the root supervisor are persisted and delivered at exit (`finishTail` reaps them at once: the record is kept and the clipped handoff is relayed). A dead non-root parent's exited, unreaped descendants are never auto-reaped: they are held for the nearest live ancestor (the custodian, derived per call from the immutable parent chain; the root counts as live), and `cancelChildren` cancels live children first, then delivers each exited one to its custodian once (`holdForCustodian`: a `child_exited` signal with `custodyOf` set and a wake for a non-root custodian, a status line naming `pomtree show` and `pomtree reap` for the operator). Past `agent.rootCustodyMax` each further delivery to the operator is also an error entry and an alert; never a refusal or a drop. The API admits the custodian to read (`show`, `events`, `transcript`, `wait`) and `reap` the exited agent, and the merge guard treats the custodian as owner when the parent is done, so unmerged work still blocks a reap with a 409 `unmerged` [verified: pomtreed/src/daemon/lifecycle.ts `finishTail`, `cancelChildren`, `holdForCustodian`; pomtreed/src/api.ts `target`; pomtreed/src/lifecycle.ts `findZombies`]. Reap (`reapNow`) only moves the agent to `reaped`: the store keeps the record and its result, and no code deletes agent rows [verified: pomtreed/src/daemon/lifecycle.ts `reapNow`]. What reap ends is the hold: the budget claim, the zombie alert and the parent's obligation to collect. The reconcile loop also cancels children found under a dead non-root parent after a daemon restart, which may retry a failed cancel; that path was read but not exercised [verified: pomtreed/src/daemon/reconcile.ts].

**Child budgets are carved from the parent, never unbounded.** `carve` takes the requested amount, then the template's `budgetMicros`, then the operator default (`budget.topLevelMicros` for a root-level spawn, else `budget.defaultMicros`), and bounds the result by what the parent has not yet consumed. An explicit request above the remainder is a 409 (`budget_exceeds_parent`); an unspecified request with nothing left is also a 409; a negative or fractional amount is a 400 [verified: pomtreed/src/lifecycle.ts `carve`; pomtreed/src/daemon/lifecycle.ts spawn path]. The default and the top-level amounts are operator-decided; see the gap list for that.

**Credential non-exposure.** The upstream provider key never enters an issued agent credential. The gateway signs a scoped credential (agent id, budget, expiry, model allowlist) with a controller-only secret and returns only that and the proxy URL; the provider key is read from `model.upstreamKey` and used only behind the model proxy, and daemon config refuses to start without it [verified: pomtreed/src/gateway.ts `ProxyCredentialGateway`; pomtreed/src/main.ts `upstream`; pomtreed/src/daemon-config.ts]. A terminal or deterministic agent is never issued a credential [verified: pomtreed/src/gateway.ts].

**Workflow opt-in is closed by default.** A workflow driver may spawn a template only when its extension owner is listed in `workflow.reviewedExtensions`, the driver is registered, and the pair is granted in `workflow.templates`; `WorkflowRuntimePolicy.allows` returns false otherwise, and the grants are validated against registered drivers and resolvable templates at startup. Agents are default-deny for template use: `mayUseTemplate` in `pomtreed/src/main.ts` admits the root (the operator) or a requester that the policy allows [verified: pomtreed/src/workflow-policy.ts; pomtreed/src/main.ts `mayUseTemplate`; pomtreed/src/daemon/lifecycle.ts spawn path].

**Chat-initiated spawn is closed by default.** `messaging.allowSpawn` defaults to off, and a non-operator chat sender's spawn intent is rejected while it is off [verified: core/src/config/params-daemon.ts `messaging.allowSpawn`; pomtreed/src/daemon/messaging.ts]. `chat.approval` (routes `spawn` and `cancel`) is a second, opt-in gate that makes chat-initiated routes wait for a human; its default is an empty list, so it adds nothing until set [verified: core/src/config/params-daemon.ts `chat.approval`; pomtreed/src/main.ts `chatApproval`].

**Non-loopback UI and host listeners are refused.** `assertLoopbackOrAllowed` throws for a non-loopback bind of `ui.listen` or `host.listen` unless `listen.allowNonloopback` is set, and its message states the listener is plain HTTP. `agent.listen` is covered by a forced decision instead (Class 2, agent listener) [verified: pomtreed/src/config.ts `assertLoopbackOrAllowed`; pomtreed/src/safety-boot.ts `safetyBootErrors`].

**Template egress is closed unless the template opens it.** A template directory entry with no `egress` normalizes to `none`, and the `browse` allowlist and `browser` profiles are rejected unless they declare the egress kind they require (`allowlist` and `audited-public` respectively) [verified: template-dir/src/index.ts]. This is the rule for templates loaded from a template directory only; the built-in untemplated path is a forced decision (Class 2, untemplated egress).

**A third-party sandbox backend is guarded at runtime.** A backend provider is untrusted code behind a declaration, so pomtreed enforces the declaration instead of trusting the provider to match it. `protectSandbox` wraps the one sandbox the daemon holds, at the composition root, in two plain delegating objects (no Proxy). The guard removes every facet (terminal, connect, files, snapshots, pause, lease, images) whose capability the declaration denies or a readiness probe withheld: reading a denied facet throws `SandboxCapabilityError` naming the cause and the action, even when the provider object carries the facet (a facet that is not denied is returned as usual), and a provider that carries a denied facet is logged once as a conformance fault. A capability declared true without its facet is refused when the sandbox is wrapped, so boot fails closed. The declaration is copied and frozen when the sandbox is wrapped, and the wrappers read and expose only that copy, so a provider that mutates its own declaration afterwards (to widen a capability once admitted) changes nothing; a probe may only withhold more within one wrapper, never give a capability back. The tracing decorator records every port and facet call (operation, sandbox id when known, outcome, duration, and on failure the error's class name only) through an injected sink, so operations are traceable without per-call-site code; request bodies, environment, credentials, file bytes and error messages never enter a record. Why: the capability model only helps if a provider cannot reach past what it declared, and a backend that fails or misbehaves must leave a trail that cannot itself leak the secrets the call carried. Limits: the guard checks facet reachability, not what a permitted facet does, and the local engines are first-party code wrapped the same way so there is one path. Reopen when a provider needs a facet outside the port's facet list, or a trace consumer needs request content [verified: pomtreed/src/sandbox-guard.ts `guardSandbox`, `traceSandbox`; pomtreed/src/sandbox-guard.test.ts; pomtreed/src/main.ts].

## Class 2: decisions the framework forces

A forced decision is one where pomtreed refuses to start until the operator has stated a choice. The framework supplies no default because any default would be a guess about the operator's trust model.

**Chat sender allowlist.** When any chat-rank channel is enabled, `POMTREED_MESSAGING_SENDERS` must list the permitted `channel:sender` pairs. `messagingSendersError` returns a refuse-to-start message when the list is empty (and rejects malformed entries), and `pomtreed/src/main.ts` prints it and exits [verified: pomtreed/src/channels.ts `messagingSendersError`; pomtreed/src/main.ts]. Configurations with no channel, with only the UI channel, or with only operator access need none. The variable is deliberately not a registry key, because it is access control owned by its operator (it is listed in `core/src/config/exclusions.ts` as `not-a-parameter`, "access control, configured by its owner"), which is why it has no key entry in `docs/configuration.md` [verified: pomtreed/src/main.ts; core/src/config/exclusions.ts].

The forced decisions after the sender allowlist refuse to start together: `safetyBootErrors` (a pure module, called from `pomtreed/src/main.ts` right after the sender-allowlist check, before any state is created) returns every violation, each naming the key, the cause and the action, and pomtreed prints them all at once and exits 1 [verified: pomtreed/src/safety-boot.ts `safetyBootErrors`; pomtreed/src/main.ts]. There is one explicit key per decision and no acknowledge key.

**Egress sidecar image.** `agent.egressProxyImage` must be set to a digest-pinned image (`name[:tag]@sha256:<64 hex>`) or a local image id. Every container spawn runs an egress-proxy sidecar, and without a pinned image the sidecar would run the worker's own image, so a template author would choose the egress enforcer. The sandbox-docker adapter's own fallback to the worker image is unchanged, but pomtreed always passes an image [verified: pomtreed/src/safety-boot.ts; sandbox-docker/src/docker.ts `egressImage`].

**Untemplated egress.** `agent.untemplatedEgress` must be `none` or `registry`: it is the network reach of a spawn that names no template (the built-in `code` template). The library fails closed to `none` when the dependency is absent, and resume and adopt read the persisted spec, so existing records keep their old egress [verified: pomtreed/src/safety-boot.ts; pomtreed/src/daemon/tree.ts `defaultSpec`; pomtreed/src/daemon-types.ts]. Requiring a template for every spawn instead is planned but not designed.

**Extension approval.** `extensions.approval` must be `none`, `all` or a comma list of extension names; there is no fallback derived from the escalation channels. The warning for approval required with no outbound escalation channel stays, and the gated action fails closed [verified: pomtreed/src/safety-boot.ts; pomtreed/src/main.ts].

**Agent listener.** `agent.listen` may be unset or `off`, a loopback host, or the detected docker bridge gateway. Any other explicit host (including `0.0.0.0` and `::`) is refused unless `listen.allowNonloopback` is set. `ui.listen` and `host.listen` keep the Class 1 rule [verified: pomtreed/src/safety-boot.ts; pomtreed/src/agent-net.ts `planAgentListen`].

**Merge check.** `merge.check` set while no check runner is wired is refused, because every merge would otherwise fail closed with `check_unavailable`; unset it until a runner exists [verified: pomtreed/src/safety-boot.ts; pomtreed/src/main.ts]. A production check runner is planned but not built.

**Load directories.** `templates.dir` (re-read on every spawn) and `extensions.dir` (read at boot) must not overlap any host path an agent container can write; otherwise an agent could change what pomtreed later loads. The writable set is the workspace clones (`<state.dir>/workspaces`), the per-agent Pi dirs (`<state.dir>/agents`), `session.dir`, `envCache.dir` and the daemon socket (`socket.path`); `repo.dir` and the mirror are never mounted. Paths are compared as realpaths (symlinks followed, the nearest existing ancestor resolved for a directory not yet created), and any overlap in either direction refuses the start: equal, inside, or containing (so pointing a load dir at `state.dir` is refused). False-positive risk: an operator who deliberately shares a writable directory with a load dir is refused, and so is a load dir that contains `state.dir`; the defaults beneath `state.dir` never overlap. There is no opt-out key [verified: pomtreed/src/safety-boot.ts `safetyBootErrors`, `realpathLoose`; pomtreed/src/main.ts].

The sender allowlist and `safetyBootErrors` are the precedent pattern for the gap list below: state the choice, fail closed until it is made, name the key in the error, and say what to set.

## Class 3: silent defaults (the gap list)

Each row is a safety-relevant choice the framework makes without the operator saying so. "Who decides" is the party whose choice governs now; "Planned" says whether a change is intended: "planned" means there is intent to build one, and "not planned" means the default is accepted as listed. The table is the list a reviewer can walk to see what a stock install decides on the operator's behalf.

| Silent default | Who decides today, and why it matters | Planned |
| --- | --- | --- |
| Zombies are held until someone disposes of them | A child's `disposition` (`hold`, the default, or `reap-on-exit`, with an optional `ttlMs` on `hold`) is declared by the parent or its template; an agent that declares nothing is held. `agent.zombieMs` only triggers an alert from `sweepZombies`; a held result is reaped by its owner or custodian, or by `sweepHoldTtl` when its TTL passes. A root child is reaped at exit whatever it declares. A TTL expiry waits while the child's merge is unsettled; a `reap-on-exit` reap bypasses the unmerged-work merge guard (reap keeps refs, the `agent/<id>` branch and the record; the notice says where the work is), and a root-custody zombie with pushed, unmerged work has no discard path [verified: pomtreed/src/daemon/sweeps.ts `sweepZombies`, `sweepHoldTtl`; core/src/template.ts `dispositionError`] | planned |
| Child budget when no one names one | `Template.budgetMicros` is optional, so the operator's `budget.*` defaults decide the carve; the carve is still bounded by the parent's remainder [verified: core/src/types.ts; pomtreed/src/lifecycle.ts `carve`] | not planned |
| Session deadlines | `session.defaultMs` and `session.maxMs` bound every session. Both must be positive; `sessionDeadlineConfig` rejects zero, so a session cannot be made unbounded through them [verified: pomtreed/src/daemon.ts `sessionDeadlineConfig`]. Listed because the default value is a policy choice made for the operator | not planned |
| Fetch identity | `workflow.fetch.userAgent` defaults to the neutral product token `pomtree`, with no contact, handle or email. Unset or blank resolves to that default where the registry resolves the key, so every layer beneath config receives a non-empty value; an operator value must be printable ASCII, at most 256 characters, with no surrounding whitespace, and start with a product token. A contact (email address or http(s) URL) is optional but recommended, and pomtreed prints one startup info line with the effective value and that advice. Sites such as the SEC ask automated clients to declare a user agent with contact details (source 1), so an operator fetching from them should add one. The product token (version stripped) is the `robots.txt` identity beside `Claude-User`, the name Anthropic gives its user-initiated fetcher (source 2) [verified: core/src/config/params-daemon.ts `DEFAULT_FETCH_USER_AGENT` and `workflow.fetch.userAgent`; core/src/config/resolve.ts (blank resolves to the default); pomtreed/src/main.ts startup info line] | not planned |
| Fetch pacing | `workflow.fetch.minIntervalMs` leaves requests to one host unpaced by default; the registry doc says to set it for sources with a rate rule [verified: core/src/config/params-daemon.ts] | not planned |
| Journal retention | `journal.retentionMs` never prunes by default, so the journal grows without bound [verified: core/src/config/params-daemon.ts] | planned |
| Operator UI | Off by default (`ui.listen`), with only the loopback rule protecting it when on. Agent-controlled text reaches the UI, and an XSS would act with operator scope through the cookie [verified: core/src/config/params-daemon.ts] | planned |
| No marker for untrusted-content agents | No template field says an agent reads untrusted content. The only distinction is the kind validation in template-dir (browse and browser templates need specific egress). A child's egress and resource limits must be within its non-root container parent's, an untemplated child's operator-wide `untemplatedEgress` included; a wider spawn is refused [verified: template-dir/src/index.ts; pomtreed/src/daemon/delegation.ts `delegationProblem`, called from `spawnNow` in pomtreed/src/daemon/lifecycle.ts] | planned |
| Supervised use is documentation only | No code detects or prevents an unattended or untrusted-input run [verified by absence: no such check in `packages/*/src`] | not planned |

The zombie row's disposition is built: a parent-declared `hold` or `reap-on-exit` with an optional TTL and a default taken from the template (`ResultDisposition`, `pomtree spawn --disposition` and `--ttl`). A precedent for the TTL is Kubernetes `ttlSecondsAfterFinished`, which deletes a finished Job once a timer expires (source 3).

## Prompt injection posture

Prompt injection is recorded as an accepted risk and is not mitigated. SPEC.md states it, in "Template prompt and browsing profiles", for the experimental `interactive` browser profile: page content reaches the model, the tool list and audited proxy bound what a steered agent can do but do not stop in-page actions, and the template's instructions to treat page text as untrusted data are not enforced [verified: SPEC.md]. The templates' untrusted-data instructions remain prompt text only. What limits damage today is structural: egress allowlists, the audited proxy, and the absence of a shell in `browse` templates (`browse` offers `web_fetch` only) [verified: SPEC.md; template-dir/src/index.ts]. No document found in this repo extends the acceptance beyond the browser profiles, so for other agents that read untrusted text (a workflow digest, a code agent given a hostile repository) the risk is unrecorded rather than accepted. The supervised-use limit above is what covers them today.

## Operator input into the agent's browser

Decided, not built. Operator input into an agent's browser page is allowed only behind a per-window flag that defaults to off, so every browser window is read-only unless the operator turns input on for that window. While the flag is off, closing the socket with code 1008 on any client data message is an invariant of this rule, not only today's behavior [verified: SPEC.md, "Live view and operator UI"]. Only an operator, through the operator-only browser route, can turn the flag on or off. When input is on, these rules apply. First, the agent is told: a notice in its context when control is taken and when it is returned, because an agent must not read a page an operator changed without knowing. The daemon generates the notice and never derives it from the page; it is journaled and delivered before the first input event is applied, and if it cannot be delivered, input is refused (fail closed). Second, one controller at a time: one operator holds control of a window and every other viewer stays read-only. Third, the flag is per window, so turning it on for one window changes nothing for any other.

Rationale: operator input lands in a page the agent reads and acts on, so it changes the agent's inputs and, through a logged-in page, may act with the operator's authority inside the agent's session. A closed default keeps the live view observation-only until an operator chooses otherwise, matching the closed-by-default rules in Class 1, and the notice keeps the agent's picture of the page honest. SPEC.md states the rule in brief and links here.

Open for the implementation, not decided here: which `Input.*` CDP methods are allowed, with their parameter validation and rate caps; whether the agent is paused while an operator controls the window or only told; how a second operator's request for control is handled (refused or handed over); how control is released (disconnect, idle timeout, or the flag turned off mid-control); and where the flag lives and how it is shown in the UI. The allowed-method list stays the frozen three-method screencast set until that is decided.

Reopen when operators must click into pages in practice, or when the agent's context cannot carry the notice reliably.

## Adding a new safety decision

Classify the decision first. If a wrong choice cannot be undone or is unsafe to guess, make it an invariant (no key; enforced in code, with the rule stated in SPEC). If the safe value depends on the operator's trust model, make it a forced decision. Use a silent default only when a safe value exists for every deployment, and then list it in the gap table so it is visible. Prefer forced over defaulted when unsure. Refuse hard: a dangerous decision stops the daemon (or the operation) with a message naming the key, and there is no single acknowledge key that waives several decisions at once; each decision has its own key. The dangerous set is built and listed under Class 2. The listed-default set, which stays a silent default but must appear in the gap table: fetch identity, fetch pacing, journal retention, session bounds and the template budget.

Copy the sender-allowlist or `safetyBootErrors` pattern for a forced decision: a pure function that returns the refusal message (so it is unit-testable without the daemon), called at startup, with an error that states the cause and names the key or variable to set; keep the logic in a pure module and the exit in the thin shell, as [`CONTRIBUTING.md`](../CONTRIBUTING.md) describes. Add a test per failure class, including a negative variant that the safe configuration passes. A decision that is deferred rather than made is recorded in the gap table with its current behavior. If a key is added or its exclusion changes, run `pnpm gen:config` in the same change so `docs/configuration.md` stays in step.
