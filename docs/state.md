# Durable state

Keyed JSON documents that outlive a run, for extensions, workflows, agents and standalone tools. This file is the model; the contract is `StateStore` in `packages/core/src/ports.ts`, the realization is `openStateStore` in `packages/store-sqlite/src/state-store.ts`, and the daemon routes are `state-routes.ts` and `state-policy.ts` in `packages/pomtreed/src`.

## Model

A document is addressed by an owner and a key. The owner is an extension name (or `operator`) and is the namespace: one owner's keys never collide with another's. A key is a slash-separated path (`StateKey`, rules in `STATE_KEY_RE` and `validStateKey` in core); `seen/hn` and `memo/<hex>` are examples. A value is any JSON value within the per-document limit.

Every document has a `rev`, a counter that starts at 1 and increases on each write. It is the concurrency token: `put` with `expectRev: null` (or `0`, "absent") creates only if the key is absent, with a number it is a compare-and-set, and with neither it is a blind overwrite. An expected conflict is returned as `{ ok: false, reason: "conflict", currentRev }`, not thrown; `currentRev` is the live document's rev and `0` when the key is absent (never written, removed, or purged), so retrying with `currentRev` is always a valid next step. `rm` of one key takes a number only (`0` = must be absent, removing nothing); `null` is refused, since a removal has no create reading. Every mutating call carries an idempotency key, scoped to the owner and the verb and bound to the writer (a key reused under another owner is independent; reused by another writer or for a different request it is `idempotency-mismatch`). A replayed key returns the first result (a stored `put` result keeps the document's metadata only and takes the value from the replaying request, which the key's fingerprint binds to the first), but idempotency rows are pruned, so replay after retention is protected only by `expectRev`. A conflict is itself a stored result, so a retry after a conflict uses a fresh key. A writer is exactly `{ operator: true }` or `{ agent, host, generation }`; an agent the registry does not know is `unknown-writer` (HTTP 403).

Removal is a hard delete with a tombstone: the value is erased and the row stays with its `rev`, so a later create continues the counter rather than restarting it. A tombstone reads as absent and does not count against the document or byte quota; instead tombstones are capped per owner (`maxTombstones`, default 1000). When a removal pushes an owner past the cap, the oldest tombstones (by removal time, then key) are purged in the same transaction and the owner's rev floor rises to the highest rev purged; a key with no row (never written, or purged) starts at floor + 1, so revs never restart and a CAS token from before the purge can never match a new document. For an owner with no purges the floor is 0 and a new key starts at rev 1. The floor lives in the `state_floor` table (part of the state schema chain, `STATE_SCHEMA_VERSION`). A migration first writes a fresh `<db>.pre-v<N>.bak` copy of the database (`backupBefore` in `packages/store-sqlite/src/db.ts`), replacing any left by an earlier attempt, and once the migrated database passes a full integrity check deletes the older `.bak` files (`pruneBackups`). The newest `.bak` can therefore still hold data the operator erased, until the next migration replaces it; erasing it sooner is a manual delete.

Limits (document count, bytes per document, bytes per owner, tombstones per owner) are store options, never call arguments; the defaults are `STATE_LIMITS_DEFAULT` in core. Operators override them with `POMTREED_STATE_LIMITS`, parsed by `parseStateLimits` in core and clamped by `clampStateLimits` (`maxDocBytes` to `STATE_DOC_BYTES_CONFIG_MAX`, `maxTombstones` to `STATE_TOMBSTONES_CEILING`). The daemon and standalone tools (the hn-digest entry reads the same env) use the same function, so they apply the same quotas to the same file. `STATE_DOC_BYTES_CEILING` (1 MiB) remains the database's hard CHECK; the configurable per-document maximum is that less 16 KiB, so the largest document plus its request envelope always fits the daemon's 1 MiB JSON body limit (`MAX_BODY` in `packages/pomtreed/src/server.ts`). Larger payloads are not a goal: `pomtree state import` sends batches of at most about 900 KiB, each under a key derived from the invocation's key (`<key>:b<i>`; a single batch uses the key as is), so a retry or a re-run with the same `--key` replays finished batches. Batches are separate calls, so a refusal part way (a quota, say) leaves the earlier batches written; the CLI reports how many documents were already imported.

Access is by writer and grant. The operator may use every owner and verb. An agent is fenced by its generation and needs a grant (`POMTREED_STATE_GRANTS`: owner, optional prefix, mode `r` or `rw`), default deny; a child's grants must be a subset of its parent's (`grantSubset` in `state-policy.ts`). A workflow handler reaches its extension's owner through `ctx.workflow.store`; its keys are scoped to `<workflow>/i/<instance>/` (or `<workflow>/g/` without an instance), which comes out of the 128-character key bound, so a handler's own key has `128 - scope length` characters (for example 113 under `digest/i/daily/`). A longer key is refused up front with a 400 that names the budget. A standalone tool opens the database itself and writes as `{ operator: true }`.

## CLI

`pomtree state ls | show | put | export | import | rm` (`packages/pomtree/src/state.ts`; verbs and flags are in the pomtree help and README). `ls` prints `(more after K)` when a page is full; continue with `--after K`. For example `pomtree state show hn-digest seen/hn` and `pomtree state rm hn-digest seen/hn`.

## Where it lives

State is its own SQLite file, `<stateDir>/state.sqlite`, next to the production `pomtreed.sqlite`, with its own schema version chain (`STATE_SCHEMA_VERSION`). The reason is blast radius: a standalone tool (the hn-digest entry is one) can read and write state without opening, migrating or locking the production audit and registry database, and the two files are backed up, erased and migrated independently. Both files may be open at once; the state file uses WAL and a busy timeout. The state dir is resolved as in `packages/pomtreed/src/main.ts`: `POMTREED_STATE_DIR`, else `~/.pomtreed`. Standalone tools must not create the directory, so a typo cannot start an empty store.

Reopen trigger for per-extension files: extensions running out of process or under another uid, a per-extension erasure, retention or encryption requirement, or tenancy.

## Convention: memoization

Memoization is a convention over the store, not a port. The owner is the workflow's extension. The key is `memo/<memoKey>`, where `memoKey(input, templateDigest, codeVersion)` (`packages/core/src/memo.ts`) is the SHA-256 of the canonical JSON of its arguments, so a changed template or code version misses. The value records the produced reports (ids or content hashes), when, and an `expiresAt`.

- Writers create with `expectRev: null`; losing the race means someone else already stored an equivalent result.
- Expiry is checked by the reader; an expired entry is treated as a miss and may be overwritten with a CAS on the rev just read.
- A hit is trusted only after the content hash of each referenced report is re-verified against the `ReportStore`; a mismatch is a miss.
- Only the owner's workflow driver holds `rw` on `memo/`; agents get at most `r`.
- Eviction is operator-driven: `pomtree state rm <owner> --prefix memo/ [--older-than 30d]`.
