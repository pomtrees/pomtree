## Waiting, yielding and interrupts

An agent's `pomtree wait`, `pomtree inbox --wait` and `pomtree ask --wait` that would block longer than `POMTREED_WAIT_YIELD_MS` ([default](configuration.md#parameter-reference)) yield under the hood: the container is released and the agent resumes later with a message such as `Resumed: child <id> exited (succeeded). Result: …`, `Resumed: your question was answered: …` or `Resumed: wait … timed out after N s`. `--interrupt` (operator only) aborts a running agent's turn, checkpoints it and resumes it at once with `Your previous turn was interrupted by the operator … Operator message: …`; a yielded agent is woken at top priority whatever it waits on. Over HTTP: `POST /v1/agents/:id/message {body, mode?: "queue"|"interrupt", idempotencyKey}` replies with `{mode, delivered: "queued"|"woke"|"interrupting"}`.

## Commands in depth

The commands, grouped. `pomtree --help` is the authoritative command, flag and exit-code list (`pomtree merge` has its own exit-code table below); there is no separate admin binary. Output is human-readable, or JSON with `--json`. `pomtree` is one binary for operators on the host and agents in sandboxes; the daemon enforces scope, not the client.

| Group | Commands |
| --- | --- |
| Lifecycle | `spawn` (`--template`, `--disposition hold\|reap-on-exit`, `--ttl`), `wait`, `reap`, `result`, `yield`, `resume` (operator; `--force` overrides quarantine; an agent may resume an exited, unreaped child or descendant it started, to resolve a merge conflict), `cancel`, `kill`, `abandon` (operator: end a run whose sandbox backend is gone; kills the sandbox on the backend its record names, or reports where it was left), `drain` (operator: stop admission, leave containers adoptable), `await-user` |
| Observe | `ps`, `tree`, `show`, `logs [-f]`, `trace`, `top`, `budget`, `spend`, `escalations ls\|answer` (operator), `decide <approval-id> approve\|deny\|pass`, `answer <escalation-id> <text>`, `pass <escalation-id>`, `models`, `whoami`, `doctor` |
| Git (agent) | `push [--branch NAME]` (bundle this clone's branch and send it to the daemon; run it before finishing; a non-fast-forward push is refused: run `pomtree pull`, fast-forward your branch onto the ingested tip, then push again; `--force` is operator-only), `pull [--from AGENT]` (fetch the default branch and ingested agent branches into `refs/remotes/pomtreed/*` and `refs/remotes/pomtreed-agents/*`), `merge CHILD [--into BRANCH]` (see Merging below) |
| Messaging | `inbox`, `peers`, `send`, `ask` |
| Reports | `report publish\|list\|show\|rm` |
| Schedules | `sched ls\|add\|rm\|pause\|resume` (cron with time zone, missed-run, overlap, jitter) |
| Templates and extensions | `template ls\|show`, `ext list\|call\|search\|fetch` |
| Workflows (operator) | `workflow launch OWNER/NAME --input JSON --key K` (source only; see Workflows below) |

An in-sandbox guide (`packages/harness-pi/src/agent-guide.md`) is injected into every agent and covers the process model, the reaping rule, budgeting, branch discipline, and idempotency.

**Debugging traces.** The Chat tab's **Copy trace** button (options caret: include children, raw tool output, Download `.md`; **Short** copies the header, last 40 events and errors) and `pomtree trace ID [--children] [--raw] [--short] [--out PATH]` produce one paste-friendly Markdown document: agent facts, budget, every journal event with tool calls paired to results, and a daemon config footer. Credential-looking values are redacted (`[REDACTED:<kind>]`, count in the header) unless `--raw` / the raw toggle is used. Operator scope only (`GET /v1/agents/:id/trace`).

**Git.** Each agent works in a private full clone under the state directory's `workspaces/`, cut from a bare mirror (`mirror.git`) of `POMTREED_REPO_DIR`, and commits to its own branch. Work leaves the clone only through `pomtree push`, which sends a git bundle; the daemon checks it in a quarantine repository before filing it under the agent's own refs, so no agent can write another's branch. `pomtree pull` brings the default branch and ingested branches back into the clone. A push that is not a fast-forward of the agent's ingested branch is refused unless `--force`.

**Merging.** A parent runs `pomtree merge CHILD` to have the controller (the daemon) merge the child's pushed work into the parent's own branch (`--into BRANCH` names another of its own branches), then runs `pomtree pull`. The merge is atomic: the branch moves only if it has not changed meanwhile (the branch ref is updated with a compare-and-swap). A conflict returns the conflicted paths; the parent resolves it in its own clone, or resumes the child (`pomtree resume CHILD`) to do so. After three failed rounds the controller escalates to the user. A child is not reaped until it is merged or escalated. The top-level agent has no parent: `pomtree merge --into DEFAULT` (DEFAULT is the repository's default branch; no child) merges its own pushed branch into the default branch, and only with the user's approval; a missing or different `--into` without a child is refused (400), and a non-top-level agent is refused (403). Merging is within one repository; cross-repo merges are not supported. `POMTREED_MERGE_DENY` and `POMTREED_MERGE_CHECK` configure the policy (see the [parameter reference](configuration.md#parameter-reference)).

Exit codes of `pomtree merge`, and what to do:

| Code | Meaning | Action |
| --- | --- | --- |
| `0` | merged | `pomtree pull` |
| `1` | other error | read the message |
| `2` | usage error, or `--key` reused for a different merge | fix the command or omit `--key` |
| `3` | unknown child | check the id |
| `4` | denied | not allowed for this agent |
| `5` | conflict (paths printed) | resolve and merge again |
| `8` | check failed | fix the cause, merge again |
| `9` | approval pending | wait, then retry the same command (idempotent) |
| `10` | target moved | `pomtree pull`, retry |
| `11` | escalated after three rounds | stop and wait for the user |
| `12` | refused by policy (denied path, bad ref) | not retryable; change the branch |

Any other daemon reply is mapped from its HTTP status like every `pomtree` command (a plain 409 gives `5`, 404 gives `3`).

**Results and disposition.** An exited child stays unreaped (held) until its parent collects it. `pomtree spawn --disposition hold|reap-on-exit [--ttl DURATION]` lets the spawning parent declare what happens instead (a template can set a default; `--ttl` alone means `hold` and is a usage error with `reap-on-exit`). `reap-on-exit` reaps once the parent was told; `hold` with a TTL reaps after the TTL, measured from the exit, once the owner was told, and the notice names the `agent/<id>` branch and `pomtree pull --from`. If the parent dies, its exited descendants are held for the nearest live ancestor and never auto-reaped; when that is the operator, a status line says `pomtree show` and `pomtree reap`, and past `agent.rootCustodyMax` each further delivery is also an alert. The operator can read and reap them. Children of the top-level agent are reaped at exit whatever they declare; their reports are kept until `pomtree report rm` if the child never pushed. Reap keeps the record, the result and the branch. A TTL expiry waits while the child's merge is unsettled (the unmerged-work check that guards a plain `pomtree reap`): the child stays held past its TTL, one `ext.pomtreed.hold_ttl_deferred` journal row on it names the merge state and the fix (`pomtree merge <id>`, then `pomtree reap <id>`), and the first sweep after the merge settles expires it. `reap-on-exit` reaps skip that check: the parent declared the reap for that child.

**Resuming.** `pomtree resume ID` wakes a yielded agent from its latest checkpoint. With `--force` (operator) it also overrides a watchdog quarantine, bumps the agent's generation (the fencing token), and accepts an agent in the `running` state. Caution: forcing a resume of a running agent fences its current run, so output from that run is rejected. Use it only for an agent whose run is stuck or dead. An agent may resume an exited, unreaped child or descendant it started, to resolve a merge conflict.

**Publishing and cleanup.** Publishing to a remote is pinned to a commit and limited to `POMTREED_PUBLISH_TARGETS`; there is no `pomtree` verb for it yet. A paused (yielded) agent keeps its folder; a cleanup sweep removes idle and reaped agents' folders later (see `POMTREED_FOLDER_*`). The daemon needs git 2.38 or newer to ingest and merge (`merge-tree --write-tree` first appeared there).

**Operator UI.** Set `POMTREED_UI_LISTEN=host:port` (default `off`) for a cookie-login web UI at `/ui`. The Inbox tab combines user-bound messages, open escalations and pending approvals, with reply, approve, deny and pass controls. Open escalation cards use the operator `POST /v1/escalations/:id/{answer,pass}` routes, including when the `ui` channel is excluded. Approvals and stream-only asks use `POST /v1/ui/reply`, which requires `X-Pomtree-UI: 1`. Reloading restores recent messages from the journal; Dismiss applies only to the current page session, so dismissed notices return after reload. Open escalation and pending approval records determine which cards need action. Channel configuration is in [Configuration](configuration.md). The unix socket also serves `/live` (agent tree, SSE), `/live/messages` (operator SSE) and `/reports`. The UI is a tiling window manager: split any tile right or down with its title-bar buttons, switch a browsing tile between the browsing views (Tree, Reports, Audit, Hosts and the other lists) from its selector (item windows have none), close tiles (closing the last one leaves an empty workspace that says "No windows open: use the launcher (Alt+Shift+P) to open one"; opening a view fills it again; on a narrow screen the one window cannot be closed), and drag a splitter to resize (a splitter will not drag a side below 160 by 120 px; arrow keys nudge a focused splitter by 5% and a double-click resets it to half). Tiles show views into agents: the terminal tile accepts keyboard input exactly as the terminal tab always has (every viewer of one agent shares that terminal), and the other views are display-only. The browser view streams the agent's headless Chromium as JPEG frames over the operator-only websocket `GET /v1/agents/<id>/browser`; it is view-only (the UI sends nothing and cannot click or type into the page), at most 8 viewers per agent are allowed, and the page, its url and title are controlled by the agent. The route and the operator UI refuse a request whose Origin does not match Host, but that check alone does not stop DNS rebinding (an attacker's hostname re-resolved to the daemon's address). The UI is safe as built because its session cookie is host-only and SameSite=Strict and bearer tokens are never sent automatically by the browser; do not rely on network position or IP-based authentication for the UI. Click a tile or press Alt+Shift+Arrow to move focus. Item windows (a terminal, a browser or a report, each showing one subject) are opened by a link such as a Tree row's terminal link: it focuses the tile already showing that subject, otherwise it splits the largest tile that can still be split along its longer side, and never retargets an existing tile; a terminal or browser appears at most once per agent and a report once per report. When no tile can be split a message asks you to close one. A link to a view that does not exist is ignored. The layout is saved in this browser's `localStorage` under `pomtree.layout` (only view and agent ids), so it survives reloads; a saved layout that cannot be read shows a dismissible message and the default layout (the unreadable text stays in storage until you next change the layout, which replaces it), and a failed save shows a message with an Export button. Export layout downloads it as JSON, Import layout loads one (errors are shown), and Reset layout restores the default; all three are in the top bar's menu (the "..." button). The top bar has a Start button that opens the launcher (an omnibar to focus or open views and run layout actions, also opened with Alt+Shift+P), a window list with one entry per tile and a status dot (the text "No windows open" when there are none), the connection state, an Inbox badge and the menu. On a narrow screen (640 px or less) the UI shows one view at a time, switched through the top bar's launcher, and leaves the saved layout untouched. Treat the UI as an operator surface; do not expose the port beyond a trusted network. Clicking an HTML/SVG/image report renders it in a sandboxed iframe (empty `sandbox`, CSP blocking script and network) at `/v1/agents/<id>/reports/<rid>/render`; markdown and text render safely in the page; downloads stay attachments.

**Driving the UI from a session.** For demos, an interactive session on the operator host (for example a Pi session with shell access) can open, move and close windows in the operator's browser tabs with `pomtree ui`; it needs the operator token, so sandboxed agents cannot (operator scope). The vocabulary is closed: `pomtree ui open terminal <agent>`, `pomtree ui open report <agent> <report>` (also `open browser <agent>`), `pomtree ui focus --dir left` (or `focus terminal <agent>`), `pomtree ui close browser <agent>`, `pomtree ui arrange grid` (re-tiles the current windows; also `single`, `columns`, `rows`), `pomtree ui reset` (default layout) and `pomtree ui follow on --views terminal,browser --of <agent>` (opens a window per child spawn while the flag is on; `follow off` stops it). Follow is a per-tab flag held in tab memory and reset by a reload, and with `--of` it covers only that agent's children. Each command is journaled as an event of kind `ext.observe.ui_command` (an audit trail) and broadcast to every tab connected to this daemon; a tab applies only commands newer than its connection and younger than 30 s, never replays history, and ignores one it already applied, so open `/ui` before you command. The CLI prints how many tabs were connected when the daemon accepted the command, which is not an acknowledgement that a tab applied it (a tab can still refuse, with its own notice); exit code 0 means sent to at least one tab, 2 usage error or daemon rejection, 3 recorded but no tab connected, 5 the `--key` was already used for a different command (use a new key or omit it), 1 unexpected reply. On a narrow screen `arrange` is ignored with a notice, more than 16 tiles raises a notice, and each tab holds three streams against the global 64-stream cap. Commands are validated against the closed vocabulary, unknown keys are rejected, and a command is data, never code. Not yet exercised in a real browser.

**Window menu, zoom and minimize.** The operations are on a right-click menu on a window entry in the bar and on a tile's title bar: Restore (shown only when it applies), Maximize, Minimize, then Close, Close others, Close to the left, Close to the right and Close all. An item that would do nothing is shown disabled (for example Close to the left on the first entry). When a command does nothing, for example from `pomtree ui`, the page shows a notice of the form "X does nothing here: <reason>". The menu also opens from the keyboard: the ContextMenu key or Shift+F10 on a focused bar entry, tile-bar control or the tile itself. Arrow keys move between enabled items, Escape closes it and returns focus to where it opened, and picking an item closes the menu first. While a menu is open the bar does not rebuild. The tile bar has Minimize and Maximize/Restore buttons before Close, and a double-click on the tile title toggles maximize.

From a session, besides `close VIEW [AGENT [REPORT]]` (one window), `pomtree ui close` takes one scope flag, relative to the named window's place in the launcher bar (reading order, hidden windows included): `--others`, `--left` or `--right`, and `pomtree ui close --all` takes no window and leaves an empty layout, which stays valid. Two scope flags together are a usage error (exit 2). `pomtree ui maximize VIEW [AGENT [REPORT]]` zooms one window to fill the whole tiling area while the layout underneath is kept, and `pomtree ui restore` with no window ends the zoom. `pomtree ui minimize VIEW [AGENT [REPORT]]` removes the window from the visible tiling but keeps its entry in the bar, dimmed and labelled "(minimized)" (hidden but listed); `pomtree ui restore VIEW [AGENT [REPORT]]` brings a minimized window back and focuses it. `pomtree ui close --focused`, `maximize --focused` and `minimize --focused` act on the focused window without naming it (`close --focused` also takes `--others`, `--left` or `--right`); with no window focused the tab shows a notice and does nothing. The commands are the same operations as the browser controls, so one rule set serves both. Exit codes are those above, and each is journaled as `ext.observe.ui_command` like the other verbs.

Rules. A minimized window keeps its place in the bar as a dimmed entry with a dashed border and the accessible name "<label> (minimized)"; a click restores and focuses it. Maximizing a window focuses it and shows only that tile; focusing another entry (a bar click or `ui focus`) moves the maximize to that window, so entries act like tabs, and directional focus has no neighbours while maximized. Closing the maximized window restores the tiling. Minimizing the maximized window ends the maximize and hides it; minimizing another window while one is maximized only hides it. Minimizing the focused window moves focus to the nearest shown window. A window opened from the launcher, a link, `ui open` or `follow` while one is maximized ends the maximize first and is then placed as usual, so a new window is always visible. `arrange` ends any maximize, re-tiles the shown windows and moves minimized windows after them in the bar order; `arrange single` keeps only the focused window and so drops minimized ones. When every window is minimized the area shows "All windows are minimized: click one in the bar to restore it." and the URL hash is cleared. A window that is maximized or minimized is not mounted: a terminal in it reconnects and replays when it is shown again.

Narrow screens (one window at a time): Close and Close all are enabled in the menu and the tile Close button, and replace the visible window with the default view, leaving the saved desktop layout untouched; Close on the default view does nothing and a notice says so. Close others, left and right are disabled because the bar lists one window; Maximize, Restore and Minimize are hidden because the window already fills the screen, and a double-click on the title is ignored.

Persistence. The saved layout (the JSON in browser storage) gains two optional keys, `hidden: true` on a minimized window and `max` naming the zoomed window, written only when set; a layout saved before them loads unchanged. The URL hash is unchanged and carries only the focused window.

**Extensions and templates.** Reports, cron, and the live view are built-in extensions on an extension host; more load from `POMTREED_EXTENSIONS_DIR`. `web_search` and `web_fetch` are proxied through the daemon (`POMTREED_SEARCH_PROVIDER`/`POMTREED_SEARCH_KEY_FILE`). Spawn templates live in `POMTREED_TEMPLATES_DIR`. Network egress is always enforced: agents sit on an internal network behind a filtering proxy, and a template's egress policy is `none`, `registry` or an `allowlist`; a spawn with no template runs the built-in `code` template, whose egress is the operator's choice (`POMTREED_AGENT_UNTEMPLATED_EGRESS`, `none` or `registry`, required); an unknown policy fails closed. A fourth kind, `audited-public`, lets an operator-authorized workflow or template reach public HTTP and HTTPS destinations through a filtering proxy that audits each CONNECT target, outcome and byte count (not HTTP content). It is never a global mode and does not change the defaults; private and host addresses stay denied. The filtering sidecar runs the image in `POMTREED_AGENT_EGRESS_PROXY_IMAGE`, which is required (a digest-pinned image, or the agent image's local id from `docker image inspect --format '{{.Id}}' <agent image>`), and `web_fetch` runs on the host network under its own scope check. Design: [`SPEC.md`](../SPEC.md#audited-public-egress).

**Workflows (source only; none enabled by default).** `pomtree workflow launch OWNER/NAME --input JSON [--key K] [--budget $USD|MICROS] [--deadline DURATION|0]` (operator only) launches a registered workflow instance through `POST /v1/workflows/launch`; `--input` defaults to `{}`. No extension owner is approved by default, and the chat workflow allowlist defaults to deny, so a default install launches nothing, from the CLI or from Discord (`!workflow launch OWNER/NAME INSTANCE`, which takes no JSON or options). Enabling a workflow is an explicit operator opt-in: list its owner in `POMTREED_WORKFLOW_REVIEWED_EXTENSIONS`, and grant its driver templates in `POMTREED_WORKFLOW_TEMPLATES` (both in [Configuration](configuration.md#configuration)). Both are validated strictly at startup. Each worker is checked against its requester's immutable workflow driver and the configured grant; anything not granted is denied, and no agent can assert its own input authorization. Operator root behavior is unchanged. This is cooperative trust, not isolation: workflow code runs in-process and is not sandboxed. The worked example is [examples/hn-digest/README.md](../examples/hn-digest/README.md) and the operator guide is [examples/hn-digest/CONTENT.md](../examples/hn-digest/CONTENT.md). Known gap: the example's live-run evidence is partial; its offline tests are the reproducible part, and live runs need explicit scoped authorization.

The metadata-only Hacker News digest API mode still works alongside the content pipeline (per-story capture and analysis); its use is in [CONTENT.md](../examples/hn-digest/CONTENT.md), and its live-run proof is partial (see above). Actual provider execution is gated separately. The approved egress profile for its workers is `audited-public` ([`SPEC.md`](../SPEC.md#audited-public-egress)). Coordinators and spawned containers need their own bindings, and that wiring is not yet complete. Model spend and provider routes are never granted by network configuration.

**Messaging.** `messaging-discord` and `messaging-stdio` (a terminal adapter: `#<esc> text` answers, `@<agent> text` signals, `!status` and `!cancel`; variables `POMTREED_URL`, `POMTREED_MESSAGING_TOKEN`, `MESSAGING_STDIO_SENDER`, `MESSAGING_STDIO_CHANNEL`, `MESSAGING_STDIO_POLL_MS`) are host adapters; the Discord one handles escalations (`pomtree ask`), answers, and `!` commands (verbs in `packages/messaging-discord/src/grammar.ts`; the adapter replies "not supported yet" to those it cannot route). Channel and sender configuration (`POMTREED_MESSAGING_CHANNELS`, `POMTREED_ESCALATION_CHANNELS`, `POMTREED_MESSAGING_SENDERS`) and the adapter's own `DISCORD_*` variables are in [Configuration](configuration.md#configuration). The adapter asserts the `x-pomtree-messaging-api` response header against `MESSAGING_API_VERSION` from `core` and refuses a 2xx without it or with a different value. `!ps`, `!budget AGENT` and `!report AGENT` are supported through the host token's read-only routes: `GET /v1/host/agents` (optional `?state=`), `GET /v1/host/agents/:id/budget` and `GET /v1/host/agents/:id/report`. Each needs `?sender=`, which goes through `POMTREED_MESSAGING_SENDERS` and a limit of 30 per minute per sender (100 per minute overall); an unknown agent returns 404.

## Spend and telemetry evidence

Spend surfaces answer different questions. Use the debit ledger for budget decisions; use the journal and traces to explain the recorded activity. The model proxy's charge is metered spend, not a provider invoice ([terms](economy.md)); pricing configuration is in [Configuration](configuration.md#configuration).

| Surface | What its figures mean |
| --- | --- |
| `pomtree spend` / `/v1/summary` | Fleet total of each agent's own settled debit-ledger spend. In-flight reservations and child budget grants are not additional settled spend. |
| `pomtree budget` (inside an agent) | That agent's budget and remaining authority after hierarchical commitments. Commitments include own spend, in-flight reservations and child holds, so remaining authority is not simply budget minus own spend. The shared arithmetic is `budgetLedger` in `packages/core/src/budget-ledger.ts`. |
| `pomtree tree`, `pomtree top`, `/live` and trace usage totals | Reported usage from retained journal entries. A row's cost is the agent's own known usage cost; its `left` is budget minus that displayed cost, without child holds. These figures can differ from the debit ledger and are not permission to spend. |

When reconciling a model call, inspect the usage event's `costSource`: `settled` means an exact provider-response-ID join to the proxy charge; `catalog` means the daemon substituted a catalog price; `harness` means it kept the harness's report. A joined event retains the harness figure as `harnessCostMicros` when present. Count a joined charge once per agent and request ID, and do not add its `ext.pomtreed.model_settlement` charge again. Likewise, sum agents' direct costs once for a fleet total; adding both subtree totals and their children counts the same work twice. The event contract is `HarnessEvent` in `packages/core/src/types.ts`.

Unknown is not free. A usage cost of `null` means no cost was reported; the daemon substitutes a price where it can. The tree renders remaining unknown costs as `unknown` or a lower bound (`>=`), with `left` an upper bound (`<=`). A reported zero with nonzero tokens can trigger catalog pricing, so it does not establish a free provider call. The proxy can charge a reservation or an estimate when usable pricing is unavailable or a stream is cut; that is a recorded budget charge, not a measured invoice amount. A zero journal total may also mean no usage was recorded or retained. Check settlements and the debit ledger before concluding that nothing was spent.

Updates arrive when the proxy settles a request and when the harness reports usage; they are not a continuous measurement of the provider's accruing bill. A long call can hold a reservation before any usage appears. SQLite journal `ts` is the controller's append time in epoch milliseconds, and `seq` orders journal entries. A debit request's `created_at` is reservation time; `settled_at` is when it reached a terminal state, including cancellation or an expired-reservation charge. These mark different points in the request lifecycle, not provider generation timestamps; a settlement's `latencyMs` measures the upstream call rather than the whole task.

Journal retention can remove old usage, tool and message entries; see `journal.retentionMs` and `journal.keepPerAgent` in [Configuration](configuration.md#configuration). Rebuilt tree views and traces cover the retained entries, so their totals and tool histories can become partial without a visible coverage boundary. The journal's incremental `spendFor` counters survive pruning, and debit accounting remains separate. Neither makes deleted trace detail recoverable. Preserve the state directory when retaining evidence ([backup procedure](../deploy/INSTALL.md)); a fresh state directory starts a different record.

Optional OTLP export sends journal-derived lifecycle and tool traces with token/cost attributes; it does not export fleet metric time series or sampled CPU, memory and disk usage. `otlp.endpoint` takes a base URL and the exporter appends `/v1/traces`. Completed spans are batched; a small run can wait for the batch threshold or daemon shutdown because there is no periodic flush timer. Delivery uses bounded retries and can drop batches; exporter counters are not an operator metrics endpoint. Configuring export or seeing a live tree is not collector-delivery evidence. Verify delivery against your own collector: the source and unit tests alone do not verify a deployment's receiver. Fleet-level metric time series and resource sampling are future work.

## Operations

For a production install (service units, env file, backup, upgrade) see [`deploy/INSTALL.md`](../deploy/INSTALL.md).

- **Startup refusals.** pomtreed refuses to start while any forced safety decision is unmade and prints all violations at once, each naming the key, the cause and the action, so one pass fixes them. The forced decisions are listed in [Safety decisions](safety-decisions.md#class-2-decisions-the-framework-forces); example values for the egress proxy image, untemplated egress and extension approval are in `deploy/pomtreed.env.example`. Setup note: the egress proxy image can be the agent image's local id, which `docker image inspect --format '{{.Id}}' <agent image>` prints (`scripts/pomtree-up`, the development launcher described under [Try it locally](#try-it-locally), fills it in for a dev run).

- **Probes.** `GET /healthz` (process answers) and `GET /readyz` are served unauthenticated on the operator unix socket only (mode 0600); the agent, host and UI TCP listeners never serve them. The body is `{status, reasons[]}` plus, when the egress audit is enabled, `egressAudit: {quarantined, retention: {spools, max, closed, open}, nearCap}`: counts only, informational, never a readiness reason. `nearCap` is true when never-closed plus quarantined audit spools reach `max - 2` (pomtreed logs one line per transition); at the cap new audited-public sandboxes are refused, the refusal names the stuck sandbox ids, and the recovery procedure is the comment above `egressSpoolRetention` in `packages/sandbox-docker/src/audit.ts`. `/readyz` is 200 when the store answers, the journal and degraded latch are clear and the sandbox is up, else 503. A probe runs `doctor`, so it has doctor's side effects. `POMTREED_READYZ_ALLOW_SANDBOX_DOWN=1` ignores a Docker outage.
- **Sandbox reachability across a restart.** Whether the sandbox backend is reachable is stored, not just remembered: each change (down, then up again) is written to the store's journal on the root supervisor as an `ext.pomtreed.host_health` entry carrying `sandboxUp` (`true` or `false`), and every later host-health heartbeat carries the current value too. pomtreed reloads the newest one at boot, so a restart during a sandbox outage starts with admission held and reports the sandbox down in `pomtree doctor` (`sandboxUp`, and the `sandbox unavailable` reason) until its first probe succeeds. The reload is bounded because the root journal is never pruned: it finds the journal's tail and reads back at most four windows of 1000 entries; if no entry is found in that range, or the store has none, the daemon boots with the sandbox up and its first probe corrects that. The entry's generation is ignored: a previous run's down entry applies, because the flag describes the host's sandbox, not any agent run. A failed write of the state is logged (`could not store the sandbox ... state`) with the action; the flag still holds admission in memory. To see the stored state, run `pomtree doctor`, or `pomtree trace <root id>`: it prints a `host_health` entry with `sandboxUp: false` as a `not ok` row, while an up entry (`ok: true`) is folded into the routine host-ok count in the header and not listed.
- **Held agents.** An agent whose sandbox is on a backend that is not the selected one (or cannot be reached at boot) is held: never inspected, resumed or killed, and the daemon starts without it. `pomtree doctor` lists the held agent ids on a `held:` line and a `next:` line with the two actions: select the backend they were started on again (`sandbox.backend`) and restart pomtreed, or end each run with `pomtree abandon <id>`. A hold does not make `pomtree doctor` fail or `/readyz` report not ready; the daemon payload carries the ids as `heldAgents`.
- **Versions and build identity.** `pomtree --version`, `pomtreed --version`, the `pomtree:` and `pomtreed:` lines of `pomtree doctor` and pomtreed's `pomtreed listening on` log line all print one string: `v<version> (abc1234)`, that is the root `package.json` version and the short commit sha of the build. An asterisk on the version, `v<version>* (abc1234)`, marks a build from a source checkout with uncommitted changes to tracked files (untracked files do not count, as with `git describe --dirty`); a dirty build is only marked, never refused. `v<version> (unknown revision)` means no revision could be found. The revision is the content of a `REVISION` file at the repository root when one exists, else `git rev-parse --short HEAD` in the checkout; a stamped revision is always reported clean. Inside the agent image, `pomtree` reports the version and revision the image build baked in (`/opt/pomtree/pomtree/version` and `/opt/pomtree/pomtree/revision`); the image build has no dirty check, so an image never shows the asterisk. The image build takes its revision from the same logic (`REVISION` file, else git), so it also builds from a tree with no `.git`; with neither it bakes an empty revision (the build prints one line saying so), and `pomtree` in that image reports `(unknown revision)`. The client/server revision mismatch warning (at boot and in `pomtree doctor`) compares the bare revisions only, so a dirty checkout at the image's commit is not a mismatch. The single implementation is `resolveBuildIdentity` in `packages/core/src/build-identity.ts`.
- **State directory.** It is realpathed at startup, must be a directory owned by the running user (else pomtreed refuses to start), and is tightened to mode 0700.
- **Database versioning.** Both SQLite databases (the store and the state store) are a single v1 baseline, stamped with a `PRAGMA application_id` (`POMS` for the store, `POMT` for the state store) and carrying a schema version (`PRAGMA user_version`). Before the first release there is no migration path: a database that has tables but no pomtree id is refused as created by a pre-release build, and any other nonzero id is refused as not a pomtree database; both messages say to move the file aside and restart to re-initialize, and development databases do not carry over. The forward-only mechanism applies to post-release changes: before a pending migration it runs an integrity check and copies the database to `<db>.pre-v<N>.bak` (N is the version before migrating; after a migration that passes a full integrity check, older `.pre-v<N>.bak` copies are deleted, so only the newest survives). A database newer than the binary is refused rather than opened, and a failed migration rolls back and aborts startup. Database files are created mode 0600.
- **Backups.** Back up the state directory before upgrading; see `deploy/INSTALL.md` for how to do it on a live daemon.
- **Crash recovery and an in-flight model call.** The model proxy reserves the worst-case cost of a call before forwarding it: the lesser of the full-output estimate and the agent's whole remaining budget (`ModelProxyService.reserve`). If `pomtreed` dies mid-call, the restart sweep charges that reservation in full and nothing is refunded; the mechanics and the reason are in [Crash semantics](economy.md#1310-crash-semantics). What an operator sees: an agent whose estimate is well under its remainder loses just that reservation. An agent whose estimate meets or exceeds its remainder held everything it had left, so the crash charges all of it and the agent ends with no budget. An agent can also park with most of its budget unspent, because the stale reservation plus its next request's estimate cover the remainder until the sweep charges it. A budget raise restores a parked agent ([Budget exhaustion and escalation](economy.md#13-budget-exhaustion-and-escalation)). Treat a crash as costing up to one reservation per in-flight call, and up to the agent's whole remaining budget.
- **Egress sidecars.** Egress proxy sidecars (`pomtree-egress-proxy-*` containers) and their socket volumes (`pomtree-egress-socket-*`) carry owner labels (store id and boot epoch), and the boot sweep removes only the daemon's own. A leftover of a stopped daemon with a different owner is not touched; check with `docker ps -a --filter name=pomtree-egress-proxy-` and `docker volume ls --filter name=pomtree-egress-socket-`, and never remove a sidecar of a daemon that is still running.

## Try it locally

Prerequisites (Node.js, git, pnpm, Docker with buildx), the clone, the install and the Linux firewall step are in [GETTING_STARTED.md](../GETTING_STARTED.md), which also builds the agent image (step 8). This section starts from a working checkout with the image built and holds two first runs: a zero-spend agent on a scripted fake model, and a first agent on a real model. A service install, which makes the safety decisions deliberately, is in [`deploy/INSTALL.md`](../deploy/INSTALL.md); `scripts/pomtree-up` (a development launcher that starts a pomtreed stack for a local trial) picks them without asking, which is why it is not an install ([Safety decisions](safety-decisions.md)).

### The launcher

`scripts/pomtree-up [PATH]` starts a blank pomtreed stack for the git repo at PATH (default `.`): state lives outside the repo (default on every platform: `${XDG_STATE_HOME:-$HOME/.local/state}/pomtree/<hash of the repo realpath>/state`, under `$HOME` so Docker Desktop shares it; `--state DIR` always wins). The default reuses existing state; `--fresh` wipes it for a blank start: an empty directory is wiped as is, a pomtreed state dir (a non-empty directory holding `pomtreed.sqlite`; only that file counts as pomtreed state) only with `--yes`, and anything else (a non-empty directory without `pomtreed.sqlite`, `/`, `$HOME`, a directory holding `.git` or the target repo) is always refused, `--yes` or not. On startup it probes that Docker can see the state dir (a throwaway container with the dir mounted read-only) and exits with a message if not. The UI listens on `127.0.0.1:8787`, and Ctrl-C stops it. It prints the UI URL, with `--show-token`, a one-click `Open:` link `http://127.0.0.1:<port>/ui#token=<operator token>`, and the `POMTREED_STATE_DIR` export for `pomtree`. The token rides in the URL fragment, which browsers never send to the server (so it stays out of access logs and Referer); the login page strips it from history and signs in. The link signs in whoever opens it and stays valid as long as the operator token does (it is derived from the state's `secret` file; a fresh start wipes state, so a new secret and token). It is sensitive in terminal scrollback and captured logs, so by default only the plain URL and the token file path are printed; pass `--show-token` to print the link (`--print-env` never includes it). `--open` launches the signed-in link (the same token-bearing link) in your browser (`xdg-open`/`open`, best effort) without printing it: the terminal and log show only the plain URL and the token file path unless `--show-token` is also given. The link is then in the opener's argv and, because `xdg-open` execs the browser (and a browser started by it keeps the URL in its own argv), in the browser's argv for as long as that process lives; any local user can read it from `/proc/<pid>/cmdline` unless `/proc` is mounted with `hidepid`. It is also in browser history (the login page strips the fragment). If other local users are a concern, do not pass `--open`; open the plain URL and paste the token from the token file. The provider is required too: `--provider NAME` (default `$POMTREED_PI_PROVIDER`). The model upstream is required: `--model-base-url URL` and `--model-key-file FILE` (defaults `$POMTREED_MODEL_BASE_URL` and `$POMTREED_MODEL_UPSTREAM_KEY_FILE`); the key file must be mode 0600 and owned by you, pomtree-up never reads or prints it, and it does not print the URL either. Flags: `--state`, `--port`, `--fresh`, `--yes`, `--keep`, `--init`, `--no-build`, `--rebuild`, `--show-token`, `--open`, `--print-env`, `--model-base-url`, `--model-key-file`, `--provider`; see `scripts/pomtree-up --help`.

`--print-env` prints the `POMTREED_STATE_DIR` export (and `POMTREE_SOCKET` when the socket was relocated) plus `alias pomtree='node <checkout>/packages/pomtree/src/main.ts'`, so `eval "$(scripts/pomtree-up PATH --print-env)"` in another terminal puts `pomtree` on hand for that stack. A missing or stale image is built with the full target under the `POMTREED_AGENT_IMAGE` tag (default `pomtree/agent:dev`). When `pomtree doctor` reports that containers cannot reach pomtreed, pomtree-up prints `pomtree-up: WARNING: agents in containers cannot reach pomtreed`; on Linux with ufw active the fix is the two rules in [`deploy/INSTALL.md`](../deploy/INSTALL.md#linux-firewall), then a restart of pomtree-up.

`pomtree` and `pomtreed` are `bin` entries that nothing puts on `PATH`. Run pomtreed by path (`node <checkout>/packages/pomtreed/src/main.ts`) and give `pomtree` an alias. `eval "$(<checkout>/scripts/pomtree-up /path/to/target-repo --print-env)"` sets the alias and the state-directory export for a launcher stack; for a daemon started by hand ([GETTING_STARTED.md](../GETTING_STARTED.md)), whose state is in `~/.pomtreed`, the alias alone is enough:

```sh
alias pomtree='node /path/to/pomtree/packages/pomtree/src/main.ts'
```

`pomtree` reads the operator token from `<stateDir>/operator.token` and refuses a token file that is not owned by you or is readable by group or others. Inside a container the daemon sets `POMTREE_AGENT_ID`, `POMTREE_AGENT_GENERATION`, `POMTREE_TOKEN`, and `POMTREE_API` or `POMTREE_SOCKET`, and `pomtree` uses those. In a script the alias is not expanded; call `node <checkout>/packages/pomtree/src/main.ts` instead.

**Environment variable prefixes.** Three prefixes appear in this repository, each with one role. `POMTREED_` is daemon and host configuration (every setting in [Configuration](configuration.md)), plus `POMTREED_STATE_DIR`, which the `pomtree` client also reads to find the state directory. `POMTREE_` is what the client and the in-container agent see: `POMTREE_TOKEN`, `POMTREE_API`, `POMTREE_SOCKET`, `POMTREE_AGENT_ID`, and `POMTREE_LIVE_*` for the live-run drivers ([`scripts/live/README.md`](../scripts/live/README.md)). `PTREE_` is test switches (`PTREE_DOCKER_TESTS`, `PTREE_NET_TESTS`, `PTREE_AGENT_TEST_IMAGE`) and variables the daemon injects into containers (`PTREE_BROWSER*`, `PTREE_CAPTURE_JOB`, `PTREE_CONFIG_JSON`); an operator does not set the injected ones.

### Zero-spend first agent

A first agent on a scripted fake model costs nothing and needs no key. There is no turnkey command for it yet (a fuller scripted demo is future work), so the steps below assemble it from `packages/testing/bin/model-stub.ts` (a scripted fake model upstream on loopback) and `scripts/pomtree-up`. They need the image from GETTING_STARTED and a shell where `docker` works without sudo.

Without a host `pi`, pomtreed has no model price list, so it cannot price the stub's usage: the model proxy answers `502 ... no usable usage the proxy can price`, the agent yields and retries on a timer, and the run never completes (each retry is charged its full reservation against the budget, no real money). `POMTREED_PI_CATALOG_DIR` fixes that by naming a Pi model catalog, which the first step below copies out of the image ([Configuration](configuration.md#configuration)). The stub also needs a script that has the agent run `pomtree result`, and none of its built-ins in `packages/testing/src/model-stub/scripts/` does: without one the agent ends turn after turn without reporting anything, and pomtreed fails the run with the cause `passive_settle`. [`examples/zero-spend/reporter.json`](../examples/zero-spend/reporter.json) is that script (it has the agent report a result and stop), and the command below passes it straight from the checkout.

```sh
c=$(docker create pomtree/agent:dev)
docker cp $c:/usr/local/lib/node_modules/@earendil-works/pi-coding-agent/node_modules/@earendil-works/pi-ai/dist/providers/data ~/pi-catalog
docker rm $c
export POMTREED_PI_CATALOG_DIR=$HOME/pi-catalog
mkdir ~/target && git -C ~/target init -q                 # a separate target repository, not the checkout
(umask 077; printf stub > ~/stub-key)                     # the stub ignores the key, but pomtreed still requires mode 0600
node packages/testing/bin/model-stub.ts --script examples/zero-spend/reporter.json --port 9911 & echo $! > ~/stub.pid
scripts/pomtree-up ~/target --init --model-base-url http://127.0.0.1:9911/v1 --model-key-file ~/stub-key --provider deepseek
```

That recipe writes `~/pi-catalog`, `~/target`, `~/stub-key` and `~/stub.pid` into your home directory; put them elsewhere if you would rather, keeping them under `$HOME` on macOS so Docker Desktop can mount them.

`scripts/pomtree-up` stays in the foreground and prints the state directory; stop it with Ctrl-C. In a second terminal, from the checkout:

```sh
eval "$(scripts/pomtree-up ~/target --print-env)"   # the pomtree alias and the POMTREED_STATE_DIR export; interactive shells only
pomtree doctor                                      # expect ok
pomtree spawn --task t --name first --model deepseek/deepseek-flash    # prints the agent id
pomtree wait <id> --timeout 60000                   # expect: exited succeeded, handoff: stub done
```

That is the whole run: an operator-spawned agent is a child of the root supervisor, so it is reaped when it exits and needs no `pomtree reap` of its own, and `pomtree show <id>` prints the kept record. Exit 7 from `pomtree wait` is only the poll timing out (the daemon caps each poll at 30 s), so run it again. `pomtree doctor` is not the firewall pass signal: it can print `agent api: off (reachable from containers)` while the container probe has failed. The pass signal is the line `pomtreed: agent endpoint container probe ok` that `scripts/pomtree-up` prints (see [deploy/INSTALL.md](../deploy/INSTALL.md#linux-firewall) if it says `FAILED`). Stop `scripts/pomtree-up` with Ctrl-C and the stub with `kill $(cat ~/stub.pid)`; the pid file works from any shell, after a restart too.

Traces and journals record tool calls raw, so they can contain whatever a tool printed, secrets included; see [Do traces and journals contain secrets?](faq.md#do-traces-and-journals-contain-secrets).

### First real-model agent

The zero-spend run proves the stack; this run swaps the fake upstream for a real provider, and it spends real money. It needs the two things the stub did not: the provider's base URL and a key.

You need an account with the provider, and a key it issues, before any of this works; the provider's own site is the only place to get one. The key is the only spend credential, it is held by pomtreed alone, and it never belongs in an environment variable, on a command line or in a chat message. Write it to a file of its own that is mode 0600 and owned by you, and give pomtreed the path; pomtreed reads the file in-process and refuses one that is readable by group or others. Agents never receive it: each gets its own scoped, expiring credential for pomtreed's model proxy instead.

```sh
mkdir -p ~/.config/pomtreed
(umask 077; : > ~/.config/pomtreed/model.key)   # create it empty and private before anything is in it
$EDITOR ~/.config/pomtreed/model.key            # paste the key yourself, then save
```

The base URL (`--model-base-url`, or `POMTREED_MODEL_BASE_URL` for a daemon started by hand or as a service) is the provider's endpoint for the model's API, and the provider name must be the same provider, because it selects the Pi provider pomtreed's model proxy serves. For OpenRouter, the default, and the model `openrouter/anthropic/claude-haiku-5.5`, the base URL is `https://openrouter.ai/api` ([OpenRouter quickstart](https://openrouter.ai/docs/quickstart), retrieved 2026-11-04). For a model served over the Anthropic messages API (as Claude models on OpenRouter are), the base URL must not end in `/v1`, because the request path `/v1/messages` is appended to it; OpenAI-compatible models use the provider's `/v1` endpoint. `--model` is `PROVIDER/ID` and splits at the first slash, and OpenRouter's own ids are `vendor/model`, so the argument carries both (`openrouter/anthropic/claude-haiku-5.5`). Valid ids come from the provider's model list: [OpenRouter lists `anthropic/claude-haiku-5.5`](https://openrouter.ai/anthropic/claude-haiku-5.5) and [DeepSeek lists `deepseek-flash`](https://api-docs.deepseek.com/quick_start/pricing) (both retrieved 2026-11-04), which become `openrouter/anthropic/claude-haiku-5.5` and `deepseek/deepseek-flash` on the command line. `pomtree models` reads the host's `pi --list-models`, so it says nothing on a machine with no `pi` installed. Start the stack the same way as the zero-spend run, with the real upstream in place of the loopback stub. Do it in a new shell, or stop the stub and `unset POMTREED_PI_CATALOG_DIR` first: the zero-spend recipe exported that variable, and a real provider prices its own usage. A different target repository, or `--state DIR`, keeps this run's state apart from the stub run's, which `scripts/pomtree-up` otherwise reuses. The agent path has been run against OpenRouter and DeepSeek, and results for a release commit are recorded in [validation.md](validation.md); other providers have not been run.

```sh
scripts/pomtree-up ~/target --init --provider openrouter \
  --model-base-url https://openrouter.ai/api --model-key-file ~/.config/pomtreed/model.key
```

Then, in a second terminal from the checkout, spawn one agent with a cap you are willing to lose:

```sh
eval "$(scripts/pomtree-up ~/target --print-env)"
pomtree doctor                                       # expect ok
pomtree spawn --task "Add a regression test for the parser" --name first-real \
  --model openrouter/anthropic/claude-haiku-5.5 --budget '$1'
pomtree wait <id> --timeout 60000                    # exit 7 just means the poll timed out; poll again
pomtree spend                                        # fleet totals; `pomtree tree` shows each agent's reported cost
pomtree reap <id>                                    # collect the result and return the unused budget
```

Three details of that spawn. `--budget` caps what one agent may spend, in dollars (`'$2'`) or raw micro-dollars; quote the dollar form so the shell leaves it alone. A top-level spawn that names no budget is carved the `budget.topLevelMicros` default out of the `budget.rootMicros` pool, so a run can cost real money without the flag; both defaults, and how a child's budget is carved from its parent's, are in [Configuration](configuration.md#budget). A spawn without `--model PROVIDER/ID` uses the default model from the host's `pi --list-models`; with no `pi` on the host's `PATH` that lookup fails ("pi --list-models failed: spawn pi ENOENT"), so pass the model explicitly, using the provider in `POMTREED_PI_PROVIDER`. A spawn that names no template runs with the network reach set by `POMTREED_AGENT_UNTEMPLATED_EGRESS`: `registry` (the value `deploy/pomtreed.env.example` and `scripts/pomtree-up` use) lets the agent reach the model proxy and the package registries only; `none` gives it no network at all, so it cannot reach the model and fails with `Connection error.` (pomtreed warns at start). Use `registry` for a first run.

For a service install rather than `scripts/pomtree-up`, the same two values are `POMTREED_MODEL_BASE_URL` and `POMTREED_MODEL_UPSTREAM_KEY_FILE` in [`deploy/pomtreed.env.example`](../deploy/pomtreed.env.example), and the service user owns the key file ([`deploy/INSTALL.md`](../deploy/INSTALL.md)). Waiting, yielding and interrupts (the `Resumed: ...` messages and `--interrupt`) are described [above](#waiting-yielding-and-interrupts).
