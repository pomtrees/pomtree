# Operator UI vision: a window manager in the browser

This document states where the operator UI is going: decisions and why, what is built, and what is open, so that separate pull requests share one reference. It is a direction, not a specification; current behavior is in [Operator UI](operating.md#commands-in-depth). "Built" means the code exists in the repository; "planned" and "speculative" mean nothing exists yet.

Terms: the operator is the person running pomtree and watching its UI; agent, daemon (`pomtreed`), extension host and journal (the daemon's ordered event log) are defined in [`README.md`](../README.md) and [`SPEC.md`](../SPEC.md), extensions in [Extending](extending.md).

The operator UI is becoming a window manager that runs entirely inside the browser. Windows are tiled and resizable, and each is a view onto what an agent is doing, not something the operator drives. A tile is one rectangular region of the screen holding one window; a view type is a kind of window (terminal, tree, report) that can be opened in a tile.

## What the operator sees

The screen is a set of tiles. The model is a file manager's (Windows Explorer). Browsing windows are lists or forms (Tree, Reports index, Audit, Hosts, Schedules, Inbox, and New agent): each is shown at most once, and its tile keeps a view selector listing only browsing views. Item windows show exactly one subject and fill the whole window apart from the chrome's own bars: one terminal per agent, one browser stream per agent (the built browser view streams an agent's headless Chromium, view-only), and one report per agent and report id. Every tile can be split, resized and closed. Item windows are opened from a browsing window, the launcher or a hash link, and are not verified in a real browser. A window whose subject is gone shows 'This agent is no longer available.' or 'This report is no longer available.' The intended set is wider: dashboards and status panes.

Chrome is one slim bar (built) and view-declared menus (built), set out in the two decisions below. The arrangement is meant to become dynamic (not built): windows come and go as agents start, finish or produce things, and extensions and workflows contribute view types, giving an extension a visible shape in the UI instead of only a route. The visual identity is black and orange, with glossy Windows XP Luna and Mac OS X Aqua style effects confined to window chrome (title bars, buttons, splitters); content areas stay flat so terminals and tables remain legible.

## Decisions and rejected alternatives

**Tiling first, not free-floating windows.** The layout is a tree of splits, which serializes to plain data, degrades to a single pane on a phone (a bottom navigation bar at narrow widths), and cannot lose a window off-screen. Overlapping windows lose both: a window can be dragged out of reach, and positions are coordinates, not a tree (general reasoning, not measured). Reopen if operators ask for overlapping windows.

**Plain browser code, no framework, bundler or new dependency.** The layout logic is a pure module and the DOM shell stays thin ([`CONTRIBUTING.md`](../CONTRIBUTING.md)); a framework or bundler was rejected because the repository allows no new dependency or build step without discussion. Reopen when the shell script outgrows isolated unit tests or a second contributor needs components.

**The layout lives in the browser's `localStorage`, with JSON export and import.** It holds only view and agent ids, no content. Rejected: a daemon journal record, because view state belongs to a device, the journal is an audit log, and it would touch the core contract; a URL hash, because URLs cannot carry a large layout and some proxies truncate them (general reason). Reopen when operators use several browsers and want synced layouts, or when several operators share a host.

**Browsing windows and item windows (built, not verified in a real browser).** A browsing window is a list or form that can be shown once; an item window shows one subject (a terminal or browser per agent id, a report per agent id and report id), has no view selector and cannot exist without its subject: the views throw without it, and a saved layout with an item tile missing its subject is rejected. Item windows fill the tile (CSS class `pane-fill` in `packages/observe/src/layoutCss.ts`, zero padding). The Reports pane stays a browsing index whose rows open `report` item windows (`packages/observe/src/reportView.ts`). Rejected: one multi-item window per view type (a Reports list with a viewer, a terminal with an agent picker), because it duplicates what the tile and the launcher already do and cannot fill the window. Reopen if operators run out of the 16 tiles with item windows, or want tabbed item windows.

**Opening an item focuses or splits; it never retargets or duplicates (built, not verified in a real browser).** From a tree name, a Reports row, a launcher entry or a hash link (`#/terminal/<agent>`, `#/browser/<agent>`, `#/report/<agent>/<id>`), the tile already showing that subject is focused; otherwise the largest tile that can still be split is split along its longer side and the new tile holds the item, so the browsing window stays (a tile at the nesting limit is skipped). Narrow mode replaces its single window. When every browsing view is already open, a split shows a notice instead of creating a tile; reaching the tile limit, or having every tile at the nesting limit, shows a notice naming which limit was hit. Rejected: retargeting the focused tile, because opening an agent from the Tree would destroy the Tree; and splitting the focused tile, because repeated openings from the Tree would halve it each time and hit the nesting limit well before the tile limit. Reopen if largest-tile placement proves wrong, for example by shrinking work in progress; that ties into the open question on automatic arrangement.

**Old saved layouts that fail validation are rejected with a visible notice (built).** There is no compatibility shim, per the pre-release rule in `CLAUDE.md`. The layout stays in `localStorage` and holds view, agent and report ids only; the hash carries the focused leaf only.

**Browser views use Chrome DevTools Protocol screencast frames, relayed by the daemon, view-only.** CDP is Chromium's remote-inspection protocol; its screencast feature pushes page frames. The daemon relays frames through a fixed allowlist of CDP methods (`ALLOWED_CDP_METHODS` in `packages/pomtreed/src/cdp-relay.ts`: start, acknowledge and stop the screencast); the viewer sends nothing, the content is labelled agent-controlled, and the debugging port is never published. VNC (remote-desktop sharing) is rejected because it needs an X server, a second protocol and port, and conflicts with the agent image's tests, which assert no VNC and no disabled Chromium sandbox (`browser-run.test.ts`, `dockerfile.test.ts` in `packages/agent-image/src`). Polled screenshots are rejected for low frame rate and fidelity. Reopen if operators must be able to click into the page.

**The black-and-orange palette replaces only the dark scheme; the light scheme is unchanged.** Because orange is now the dark accent, the dark warning colour moved to a yellow-green and the error colour to a rose, to keep status meaning.

**Views are read-only windows onto agents.** The terminal window is the deliberate, for-now exception: it still accepts keyboard input, as the terminal tab does. The browser view is view-only. Per-window read-only is open below.

**One slim bar replaces the navigation bar (built).** The bar has three parts. A start button at the left opens a launcher (a panel for opening things) whose search box is an omnibar, a single search box accepting view types, agents and actions such as "split" or "reset layout"; the launcher's list of view types comes from the view registry. A middle window list (the bar's row of entries, one per open tile) has a status dot per agent and is where an attention signal such as a failed agent appears; keeping the window list is decided. The right side shows the connection state, an Inbox badge (the Inbox view combines user-bound messages, open escalations and pending approvals, per [Operator UI](operating.md#commands-in-depth)), and one menu holding the layout actions (export, import, reset) and sign out. Each tile keeps a view selector listing only browsing views; item windows have none. At narrow widths it replaces today's bottom navigation. Rejected: the current navigation bar, because it duplicates each tile's selector, mixes view-opening with layout and session actions, and does not scale to one terminal per agent; a start menu alone, because it costs a click, hides actions and has no search; an omnibar alone, because it is not discoverable and needs a touch fallback; a taskbar alone, because tiling has no overlap, so it is only a window list and indicator (minimize exists only as the hidden-but-listed state below). Precedents (general practice): desktop taskbars, i3 and tmux status bars, VS Code's command palette. Reopen if operators find the omnibar unused or the window list too crowded with many agents. The static mock [`mockups/ui-launcher-mock.html`](mockups/ui-launcher-mock.html) is the approved visual reference; the bar is built to it, the window menus are not.

**Window-bar context menu with maximize and minimize, on one command model.** A right-click menu on bar entries and tile titles offers the usual tab set (Close, Close others, Close to the left, Close to the right, Close all) plus Maximize/Restore and Minimize; the tile-bar buttons, the double-click on the title and the `pomtree ui` verbs all call the same window commands over the layout, so there is one source of policy (usage and rules: [Operator UI](operating.md#commands-in-depth)). Maximize zooms one tile while the layout is kept; minimize hides a tile but keeps its dimmed entry in place in the bar. Both are optional keys in the saved layout. Rejected: a separate tray for minimized windows, because it makes a second list and leaves left/right closing ambiguous; a version-2 layout format, because two optional keys keep every saved layout loading; menus declared per view, because a window's menu is a host concern and the view menu ids are a closed set. Reopen if extension views need their own context items, if operators expect picking another entry to end the zoom, or if losing terminal state on maximize is a complaint.

**Omnibar, window list and narrow bar (decided, built).** Each decision is known from the code in `packages/observe/src/launcherModel.ts` (header comment), `launcherShell.ts`, `shell.ts` and `layoutShell.ts`; none has been run on every OS and browser.

- Omnibar vocabulary: open windows (focus), browsing views not shown (open in a new tile; a view already shown is focused instead), and item entries per known agent: "Open terminal for <agent>", "Open browser for <agent>" and "Open report <name> (<agent>)" (the unfiltered list is capped like the other agent entries; a typed query matches all agents, so one past the cap is still found by name or id; report names are fetched when the launcher panel opens, with no polling), and fixed actions (split right, split down, close tile, reset layout, export, import, sign out). Free text is never a command: a query matching nothing shows "Nothing matches". A leading ">" restricts the list to actions (the VS Code command palette precedent, general practice). Matching is case-insensitive, every token must match the label, kind or hint, and a word-start match beats a substring match. There is no fuzzy subsequence matching, which keeps results predictable. Reopen if operators miss fuzzy matching.
- Open key: Alt+Shift+P, matched on the physical key code so it works with any keyboard layout and while a terminal has focus. Pi uses Ctrl keys in the terminal, and Ctrl+K and Ctrl+Shift+P collide with the browser and with pi; Alt+Shift is already the tile-focus family. Unverified on every OS and browser; reopen if it collides.
- Window list: one entry per tile (at most 16 tiles, so it is bounded by the layout limit, not by the number of agents), in reading order, scrolling sideways, with compact labels above 6 entries. The status dot shows each agent's state: running ok, pending info, yielded warn, exited failed, timed out or over budget err, others none. The Inbox entry shows warn while the badge is above zero. Agents without a tile live in the launcher, not in the list. No grouping is built. Reopen if operators run more than about 6 tiles and lose attention signals off-screen; a count of off-screen attention entries is the natural next step.
- Narrow (640 px or less): the bar stays on top and replaces the bottom nav. The window list then holds the single current view, the connection pill shrinks to its dot, and the launcher opens full-width and is how views are switched (one more tap than the old bottom nav). Reopen if operators miss the bottom nav.
- Bar menu: the fixed list Export layout, Import layout, Reset layout, Sign out.
- Data: the bar polls `/v1/agents`, `/v1/approvals?state=pending` and `/v1/escalations?state=open` every 5 s while the page is visible. Connection state is derived from those polls: connecting, connected, reconnecting after 1 failed poll, offline after 3, with the cause in the tooltip. The Inbox badge counts pending approvals plus open escalations and excludes user-bound messages, which need the SSE stream: tracked by `TODO(launcher-inbox-messages)`. Polling is temporary until the menu and status data seam lands: `TODO(launcher-status-seam)`.

**Views declare their own menus and status (built).** A view no longer draws a toolbar in the content area. The window chrome renders what the view declares: a classic menu bar in the style of desktop applications (general practice, not a repository fact). Each view names its own menus from View, Trace, Session and Help: a terminal has View (font size), Trace (Copy trace, View trace, Short, the children and raw options, Download), Session (Reconnect) and Help (Keys); the browser tile is view-only, with a read-only URL and View and Help menus; the Inbox tile has a View menu that filters by kind. The state and connection pills move to the title bar or a one-line footer. Below a tile width of about 420 px (a starting value) the menu bar collapses to one overflow menu, a button listing every menu's items. The registry's `host` gains `setMenuState`, `setStatus` and `onCommand` next to `setTitle`. Decided: the first public view-type API accepts menu declarations, as plain serializable data with no callbacks; an action is a host-defined command id dispatched through a host handler, built in this menu and status seam. A declarative menu is data the host renders, in line with the rule that agent-controlled text uses `textContent` only. Rejected: a toolbar inside each view, because content never fills the window and each view invents its own layout; an overflow menu only, because it hides every action behind a click even in wide tiles; per-view-type menus implemented outside the registry, because that is a second source of policy; for the public API, keeping menus internal until the extension API settles, because extension views would then ship without menus and retrofitting changes the contract; and letting views render their own controls, because that reopens the second-source-of-policy and `textContent` problems. Reopen if the menu bar's height makes small tiles unusable, screen-reader and keyboard use proves poor, or an extension needs callbacks or richer rendering.

## Pane consistency rules (built; not verified in a browser)

Every browsing window (Tree, Audit, Hosts, Schedules, Escalations, Inbox, Reports index, New agent) follows one skeleton, so the panes look like one family. The item windows already follow it with zero inset. The drift these rules remove: the Tree and Audit panes put a control row above the table, Hosts was a three-line monospace card, New agent was capped at a fixed width, the Inbox spent several rows on status and compose, every pane sat inside a padded bezel, and each pane invented its own empty and error markup.

**Fill rule.** The primary content fills the window, bezel-less. The tile's own 1 px border is the only bezel: a pane has no outer padding, no card border, radius or shadow around its table, and no row of its own above its content for controls, titles or counters. Blank space is allowed only when the content is genuinely short (few rows); an empty state is one compact line at the top, never centered in the void.

**Controls live in the window chrome, not in the content.** A view declares controls as plain data next to its menus and status: a `button` (label, command id, optional primary) and a `search` (text field; its command receives the typed value). The tile bar renders them between the title and the menus, so they cost no content row; the footer carries the connection state and a count. Rejected: a pane-owned toolbar strip (the row the operator rejected; every pane draws its own), a floating overlay over the table (covers rows and the last column, fixed coordinates, unreachable at narrow widths), a filter row inside the table header (fits tables only), and menus only (free-text filters cannot be menu items and the primary action would sit behind a click). Precedent (general practice): VS Code view-title actions, the Finder unified toolbar, the Explorer command bar. Narrow behavior: buttons move into the overflow menu below 420 px of tile width (the existing container query); the search stays in the bar and shrinks; every control is reachable by Tab. The standalone live and reports pages have no chrome, so they keep a plain heading and the connection pill and omit actions such as New agent. Reopen if operators cannot find actions in the title bar, or the bar is too crowded in narrow tiles.

**One skeleton.** The root is `.pane` (it fills the tile: flex column, full height, no padding). Its children are an optional one-line `.pane-notice` (status or error, absent when empty) and exactly one `.pane-body`, the pane's only scroller. A table pane's body is `.tablewrap` (sticky header row, edge-to-edge cells); a list pane's is `ul.card-list`; a form pane's is `form.pane-form`, whose fields use the full width and flow into columns by container width instead of a fixed `max-width`. Shared pieces live in `paneKit.ts`: empty and error rows, the notice, card, compact button and field styles; no pane ships an inline `<style>`. There is no heading inside a pane; the tile title is the title. Text content (forms, cards, notices) is inset by one token; tables are not.

**Density and type scale.** One token set under `.pane`: inset 0.75 rem, gap 0.5 rem, table cell padding 0.3125 rem by 0.75 rem; sizes 0.75 rem (header cells, meta), 0.8125 rem (controls), 0.875 rem (body and tables), 1 rem (form fields). Buttons and fields are compact everywhere, with the 2.5 rem touch minimum kept on coarse pointers.

**Hosts is a table** (host, max, running, queued, running agents, queue), like every other list; its empty state is the shared row.

**Checked.** During the change the panes were rendered once in headless Chrome from static pages with stubbed data (wide, 420 px and a four-tile layout), before and after. That check was ad hoc and is not repeatable: the harness and its screenshots were scratch files and are not in the repository. There has been no run against a live daemon or another browser, so the real-browser check stays open as `TODO(chrome-browser-check)` in `chromeCss.ts`.

**Enforcement.** `packages/observe/src/paneSkeleton.test.ts` asserts the contract on every pane's markup and on the pane and layout CSS, and fails if a pane brings back a toolbar row, a heading, an inline style block, a root `max-width` or outer padding.

**Streaming views keep their last content under an overlay.** The terminal and browser views never clear or hide their screen or frame when the stream drops, ends or the agent goes away; `K.staleOverlay` (`paneKit.ts`) puts a semi-transparent veil over it with a text label: a spinner while connecting or reconnecting (shown after an 800 ms grace delay when there is content to keep, at once when there is none), a pause icon when nothing will be retried and nothing is wrong (a yielded agent), a danger icon with the cause when the stream is over (finished agent, gave up reconnecting, agent gone, no browser running). The overlay never takes the pointer, so text stays selectable, and the footer keeps the state text. After a terminal reconnect the old screen stays until the daemon replay's first bytes (or 1.5 s), then resets so the replay renders clean. Rejected: a status-only footer (what it was before: nothing marks the frozen content as stale), clearing the content on disconnect (loses context the operator was reading), and spinner for every non-live state (a finished agent would look like it is retrying). Reopen if operators find the 800 ms delay hides real stalls or want a manual dismiss.

**Menus should not be clipped by their tile.** While a menu is open its tile switches to `overflow: visible` with a raised stacking order, because `position: fixed` cannot escape a tile that is a container-query root (layout containment). The `:has()` rule that does this is unverified in a browser (see `TODO(chrome-browser-check)` in `chromeCss.ts`). Reopen if a menu is seen painting under a neighboring tile.

## Status

Built:

- the pure layout module (`packages/observe/src/layout.ts`);
- the tiling shell with persistence, import, export and the narrow-width fallback (`packages/observe/src/layoutShell.ts`);
- a terminal pane mountable more than once per page, and an internal view registry (`registerView` in `packages/observe/src/paneKit.ts`; not yet a public API);
- the black-and-orange dark scheme with window chrome (`packages/observe/src/themeCss.ts`), with a dark terminal palette (`termKit.ts`), splitter focus styling, forced-colors (high-contrast mode) handling, a chrome border held at 3:1 contrast or more by `themeCss.test.ts`, and an aspect-preserving browser canvas (`layoutCss.ts`);
- the live browser view, described below;
- the terminal-focus fix: a terminal mounting no longer moves the tile focus (`packages/observe/src/layoutShell.ts`);
- the view menu and status declaration (`packages/observe/src/menuModel.ts`): a view type declares per-window menus (View, Trace, Session, Help) as plain data with action, toggle, radio and separator items keyed by command id, plus status slots; `registerView` accepts them as optional `menus` and `status`, and a per-tile window model resolves one declaration into both the menu bar and the overflow list and dispatches picked commands to a handler the view registers; the window chrome (`windowChrome.ts`, `menuNav.ts`, `chromeCss.ts`) renders it in each tile: a title-bar menu bar with keyboard navigation and ARIA menu roles, one overflow button below 420 px of tile width (a CSS container query), and a status footer; the terminal, browser and inbox views declare their menus and status (`viewMenus.ts`), and the terminal's toolbar is gone from its pane;
- the pane skeleton and chrome-hosted controls described under pane consistency rules: `paneKit.ts` (`.pane`, `.pane-body`, `.pane-notice`, card list, form), `menuModel.ts` and `windowChrome.ts` (the `controls` declaration), every browsing pane migrated, Hosts as a table, and `paneSkeleton.test.ts` as the drift test;
- item windows: the subject model in the layout leaf params (`layout.ts`, `layoutShell.ts`), the terminal and browser views requiring an agent and filling the tile (`tabs.ts`, `browserView.ts`), the `report` window (`reportView.ts`), and the launcher's item entries (`launcherModel.ts`); a window whose terminal, browser or report subject is gone shows a placeholder;
- the launcher bar (with a visible hint when no window is open): a pure model (`packages/observe/src/launcherModel.ts`), the DOM shell and its styles (`launcherShell.ts`), mounted by `shell.ts` and driven through the window-manager `api` in `layoutShell.ts`.

Built today: views are registered in `TabRegistry` (in `packages/observe/src/shell.ts`, filled in `packages/pomtreed/src/ui.ts`). Each tile has split and close buttons, and browsing tiles a view selector (`layoutShell.ts`). A view registers through `PaneKit.registerView` with `{id, title, multi, mount(root, params, host), menus, status}`; its `host` offers `setTitle`, `navigate`, `setMenuState`, `setStatus` and `onCommand`.

The terminal-focus fix is a heuristic: only focus that follows a key or pointer press counts as the operator's. Two limits, tracked by `TODO(tile-focus-source)` in `layoutShell.ts`: a key held down while a terminal's socket opens still moves the tile focus, and focus moved with no key or pointer press (a screen-reader cursor, voice control) no longer updates the focused tile.

The browser view (`packages/observe/src/browserView.ts`) is served by the daemon route `GET /v1/agents/:id/browser` (`packages/pomtreed/src/browser-route.ts`). A per-agent hub (`browser-hub.ts`) shares one stream among viewers, and a relay (`cdp-relay.ts`) sends only the allowlisted methods. The daemon reaches Chromium through the sandbox `loopback` facet (`SandboxFacets.loopback` in `packages/core/src/ports.ts`), using a bridge script in the agent image (`packages/agent-image/src/loopback-bridge.ts`), so no port is published. A backend that provides no `loopback` facet refuses the browser view with a message naming the cause and the action. The Docker-gated test `packages/e2e/src/docker-browser-stream.test.ts` (skipped by `pnpm check:lite`) asserts that a real worker delivers a JPEG frame and a "live" status and that the container publishes no port and has no network.

Limits of the item windows: the standalone reports page has no window manager and no in-page preview, so its names download the raw bytes, tracked by `TODO(reports-page-viewer)` in `web.ts`.

Not built either: windows that appear and rearrange with agents; a public view-type API; layout synchronization across browsers; floating windows; and per-window read-only.

## Open questions

**Automatic arrangement policy.** When an agent appears or finishes, where does its window go? Options: append to the focused tile (simple, but disturbs reading); split the largest tile (predictable, but shrinks work in progress); open into a designated area the operator names (stable, but needs a fallback when full); never rearrange what the operator placed by hand, only fill or reclaim tiles the policy created. Recommended: the last, with a designated landing area, because the operator's own placement is the costliest thing to lose. Item windows opened by the operator already use largest-tile placement; only the placement of windows when an agent appears stays open.

**How an extension declares a view type, and what it may render.** The precedent is `UiPane` in [Extending](extending.md#4-proposed-seams-not-built-future-work), gated on an open XSS risk (`TODO(ui-xss)`): agent-controlled text reaches the UI with operator scope. Options: a declarative manifest the host renders; a function mounting into a sandboxed origin; or one mounting directly in the page. Recommended: declarative first, content set only through `textContent` as today, because it widens no exposure; a sandboxed form can follow once the XSS gap is closed.

**Per-window read-only, and whether any window may take operator input.** The terminal accepts input today; browser views are view-only by decision, and operator replies already go through the Inbox. Options: make every window read-only and remove terminal input; a per-window setting; or keep the terminal writable as a stated exception. Recommended: a per-window setting, read-only by default, with the terminal as the one enabled exception, so it keeps working while the model becomes enforceable.

`git log` restricted to `packages/observe/src` shows the built parts; the layout module, the terminal pane's multi-instance mount and the palette and chrome commits can be reviewed independently.

## UI control

The UI can be driven by operator commands (`pomtree ui ...`) so a session can stage a demo: open, focus and close windows, arrange, reset and follow spawns. Usage, delivery semantics and exit codes are in `docs/operating.md` ("Driving the UI from a session").

- **Commands are durable journal events, not in-memory fan-out.** Reason: the daemon keeps no state in memory, every mutating call is idempotent and audited, and the journal gives restart safety and an audit trail. A tab starts at the journal tail and applies only fresh commands, so history never replays. Reopen if command volume makes journal growth a problem, or if a high-rate lossy command (cursor, scroll sync) is added, which would want an ephemeral channel.
- **Follow is a per-tab flag in tab memory.** Reason: persisting a mode that opens windows unprompted across reloads would surprise the operator. Reopen if demos need it to survive a reload.
- **Presets re-tile the current windows** rather than build fixed-view layouts, which would need an agent subject and fail when a view is unavailable. Reopen if a named fixed layout is wanted; free-form layouts stay with Import.
- **Broadcast only, no acknowledgement.** Open work is `TODO(ui-command-target)` and `TODO(ui-command-ack)` in `packages/pomtreed/src/builtin/uiDrive.ts`.
